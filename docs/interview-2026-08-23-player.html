CoMotion 播放器方向訪談

2026-08-23 · Grilling 逐字紀錄整理

這是一份使用者訪談紀錄。CoMotion 是一個以 SVG 為本體、人與 AI agent 共同編輯簡報的專案。 前一個階段完成的「曳光彈」（agent 靠 CLI 命令編輯投影片）已驗證成立，這次對話決定下一個大方向： 做一個播放器——側邊總覽、點選看單頁、進入播放、方向鍵推進、支援動畫與影音播放， 這一輪刻意不做編輯功能。內容取自真實 session 逐字檔，使用者發言多為口述輸入， 已依上下文修正語音辨識錯誤、刪去冗詞，但盡量保留原本語氣；AI 的長篇分析已濃縮為要點。

本次做成的決定

  • ADR-0007 — 播放 .comot 檔案必須安裝 CoMotion；分享給他人靠未來的 Export（HTML／PDF／PPTX）功能，不靠直接傳檔（取代 ADR-0005 中「runtime 不得依賴 server」那段）
  • ADR-0008 — 一張投影片自成一體：動畫等資訊都寫在該張 SVG 內，對調兩頁不需要改任何第三個檔案
  • ADR-0009 — 動態表現是一份「有序的效果清單」，寫在 SVG 的 <metadata> 裡，不是散落在各元素的屬性上（取代 ADR-0005 的屬性設計）
  • ADR-0010 — 投影片內容視為不可信：檢視模式不跑 script（零 token sandbox iframe），只有進入播放模式才開放 allow-scripts
  • CONTEXT.md 新增「效果」「效果清單」「總覽」三個詞；修訂「步驟」（改為推導、頁內作用域）、「進場」（收窄回靜態元素出現）、「播放」（全螢幕不屬於定義本身）

前情提要

AI（背景）

在這段訪談之前，使用者先問「接下來要做什麼」，AI 盤點了現有 spec 與 issue 進度：曳光彈驗收成立， 剩餘票不急，建議下一步做「步驟驅動動畫」。使用者一度同意，但在準備進入細節訪談時， 改變主意，提出了一個更大的方向——不做動畫細節，而是先做一個完整的「播放器」樣態。 以下訪談從那個轉向開始。

方向轉向：播放器

使用者

我決定了，接下來下一個大的方向，我要在 CoMotion 這邊實現一個功能、一個樣態。這個樣態是， 它就像是一個投影片的編輯器——投影片編輯器的基礎功能都先不用，只要是說這個投影片，你可以看到它的側邊總覽， 然後點下去之後可以看到每一頁的投影片，然後你可以按播放之後放到全螢幕，按下一頁、按下面的往下鍵， 你就可以往下一個投影片走，用這樣的樣態去做。然後至於編輯方面，我先不要做編輯，就只要能播放就好了。 播放也包含影像跟音訊的播放，還有圖片的播放。這邊也要實現一些動畫，動畫最簡單，就是我按下一鍵， 假設第一個動畫 object 就出現，再按下一鍵，第二個 object 就出現。或者是說我到下一頁之後， 我原本影片是靜止的，我按下一頁，影片就會開始播放。或者是一個音訊的檔案在這個 slide 裡面， 我按下、往下按，之後它就會播放這個音檔。所以就是實現一個可以呈現投影片的這樣一個介面。 當然這些介面全部都要來自於我這個特製的 CoMotion 副檔名底下，要包含在這個裡面，然後被播放出來。 我希望你不要悶著頭就直接開始做，我覺得你應該要去上網找一下，有沒有網路上一些資訊可以拿來使用或參考， 如果可以的話就把它拉下來參考。

AI

收到，方向轉了：下一個大方向是「播放器」，不是編輯器。先照要求去查資料，再開始逐題訪談。

查到的關鍵事實：

  • 三個前案可參考：JessyInk（JS 內嵌進 SVG，但違反「SVG 是本體」的原則）、Sozi（SVG 原檔不動、runtime 匯出成外部 HTML，形狀最接近）、reveal.js（本體非 SVG，但媒體與 fragment 的行為設計值得直接抄語意，如「離開投影片自動暫停」）
  • SVG 1.1 沒有 <video>/<audio>，<foreignObject> 已被 ADR-0005 否決，所以影音只能是疊在 SVG 上的 HTML 元素
  • 自動播放需要使用者手勢，但 keydown 算數——操作模型剛好是「按鍵才播」，天然繞過這個限制
  • 現有 canvas.ts 把投影片放在零 token 的 sandbox iframe 裡，不准跑 script

問題 1播放器是獨立 HTML 文件，還是編輯器裡的一個模式？

AI

AI 引用 ADR-0005「runtime 不得依賴 server」，建議播放器是一份獨立、對 server 一無所知的 HTML 文件， 即未來 export --html 要吐出來的東西。理由：讓 ADR-0005 從紙上承諾變成可驗收條件、 一次解決 sandbox 信任邊界問題、上台簡報不必依賴跑著 server 的機器。

此處後來改變： 使用者在下一則訊息裡直接撤銷了這個建議所依據的 ADR-0005 段落，改成「播放一定要裝 CoMotion」。 本題「獨立 HTML 文件」的建議因此整個作廢，從未被採納。

撤銷 ADR-0005：播放必須依賴 CoMotion

使用者

這邊我想要撤銷對於 ADR-0005 的這段描述。我想要改成，其實就是你的電腦裡面要安裝 CoMotion， 你才能播放我這個檔案，所以反而是會有依賴，一定要 CoMotion 的。CoMotion 現在是一個 server—— 不是 HTML，是一個 server。你在執行的時候用 server mode 把它打開來，然後到相應的 port， 把網頁打開來，那就是一個編輯器可以使用。接下來你把 .comot 副檔名的檔案放進去， 這個播放器或編輯器就可以開始使用了。未來也還會進一步把它改成一個 Mac 的 app， 打開一個 app 之後你就可以去使用 CoMotion。所以這邊要做一個修改，就是修改 ADR-0005。

AI

算清楚代價：

  • 買到：runtime 可依賴 server（影音可走 HTTP Range 串流）、播放器與編輯器共用同一個 web app、未來 Mac app 只需把 server 藏起來
  • 賠掉：export --html 這扇門關上、.comot 寄給沒裝 CoMotion 的人＝廢檔，與 ADR-0003「簡報可寄送」的出發點有張力
  • 唯一逃生口更重要了：沒裝 CoMotion 的人至少能把單張 SVG 拖進瀏覽器看到靜態內容（ADR-0001 的驗收標準）

建議寫一份新 ADR-0007 來 supersede 舊段落，而不是直接改 ADR-0005 內文，理由留在原地。

補充：分享靠 Export，不靠傳檔

使用者

我同意你的建議，你就這樣修改吧。另外我要補充一下，這邊有提到這個修改賠掉什麼——其實沒有賠掉什麼， 因為我未來可以在 CoMotion 的 app 裡面，或者是 server 裡面，實作一個功能叫做 Export HTML， 或者 Export PDF，甚至 Export PPTX，這些都可以實現。你仍然可以轉換成其他的檔案格式分享給別人， 只是針對 .comot 這個副檔名，只有在 CoMotion 裡面能跑。

AI

這個補充把代價欄改寫了：不是「不能分享」，是「分享靠匯出，不靠傳檔」——.comot 是工作格式，不是交付格式。 AI 標記了一個暫不處理的張力：ADR-0001 寫著「CoMotion 不匯入也不匯出 PPTX」，與這裡提到的 Export PPTX 牴觸， 但判斷現在不需要動 ADR-0001，等真正要做 PPTX 匯出時再處理。ADR-0007 定案，問題 1 因此被回答： 播放器不是獨立產物，是同一個 web app 的一個模式。

問題 3「步驟」的作用域：一頁之內，還是貫穿整份簡報？

AI

兩個選項：

  • A. 頁內作用域 — 每頁的步驟編號都從 1 重新算
  • B. 全域連續 — 整份簡報步驟編號一路連號

建議 A，理由來自 ADR-0001（單張 SVG 應可自我解釋，不依賴它在簡報裡的位置）與 ADR-0003 （避免調整順序時要重編大量屬性）。代價：「總共幾步」不存在於任何單一檔案，得由 runtime 算出來。

問題 4「還沒出現的元素」存在檔案裡，還是只存在 runtime？

AI
  • A. 存進檔案 — 元素帶 display="none"，逐步打開
  • B. 只存在 runtime — 檔案裡所有元素都可見，靜態長相＝最終狀態，runtime 播放時才逐步隱藏／放出

建議 B，且認為 A 不合法：A 會讓沒裝 CoMotion 的人用 Illustrator 打開時看到幾乎空白的頁面， 違反 ADR-0001 的靜態相容性保證。B 讓編輯模式免費得到正確畫面，且 data-comot-step 退化成純標記，不影響渲染。代價：載入瞬間可能閃過完整內容（FOUC），是已知可解問題。

問題 5（第一版）影音的播放跟元素的進場，是同一件事嗎？

AI
  • A. 合而為一 — 同一套機制（data-comot-step + data-comot-enter），影音的「表現」就是開始播放
  • B. 分成兩套 — 出現用一組屬性，媒體觸發用另一組

建議 A，但代價是要把 CONTEXT.md「進場」的定義放寬成涵蓋「靜態元素出現」與「影音開始播放」兩種表現。

此處後來改變： 使用者要求 AI 參考 PowerPoint／Keynote 的擴充性設計後，問題 5 被重新提問（見下）， 結論改成「進場」維持原本較窄的定義，影音播放另立一個效果家族。這裡放寬定義的提議作廢。

插話：參考 PowerPoint／Keynote 的擴充性

使用者

這邊我想要跟你討論一下，因為以後會有更多的動畫轉場，不是只有出現，以後會有更多投影片播放的狀態。 所以我想要你多想一下 PowerPoint、Keynote 這一類投影片播放軟體的設計應該是怎麼設計， 這樣對未來的擴充性會比較好。

AI

查了兩家的實際資料模型：PowerPoint 的動畫存在 <p:timing>，是一棵跟形狀樹完全分開的樹， 效果是一份有序清單，媒體播放也只是清單裡的一項效果，不是另一套機制；每項效果帶起始方式 （On Click／With Previous／After Previous）。Keynote 同構。關鍵發現：「按一下」跟「一項動畫」不是一對一—— 「步驟」不該被儲存，應該是從有序效果清單推導出來的。

問題 5（重問）動畫資訊住在元素身上，還是住在一份有序清單裡？

AI
  • A. 住在元素身上（ADR-0005 原本的寫法）— data-comot-step / data-comot-enter 屬性
  • B. 住在一份有序清單裡（PowerPoint／Keynote 的形狀）— 寫在 SVG 的 <metadata>，每項指向一個元素 id

建議 B：A 有結構性天花板（一個元素只能有一種效果，無法表達「第 2 步出現、第 5 步強調」）； 順序放在清單裡讓插入/對調變成 splice，跟 ADR-0003 選 slides 陣列同一個道理； <metadata> 仍是合法 SVG，不影響其他工具開啟。代價：可能出現「孤兒效果項」 （元素被刪、清單裡的引用懸空），需要靠刪除命令一併清理。「進場」的定義因此不用放寬了， 退回只管靜態元素出現，媒體播放是另一個效果家族。

B

問題 6runtime 跑在 sandbox iframe 內，還是放棄 iframe？

AI
  • A. 維持 iframe — 播放時加 allow-scripts（絕不加 allow-same-origin），檢視模式維持零 token
  • B. 放棄 iframe — SVG 直接 inline 進主文件，改用伺服器端消毒不可信內容

建議 A：用瀏覽器打磨二十年的 sandbox 邊界，不自己扛消毒正確性。 支持論證之一：「播放永遠是全螢幕，所以沒有任何東西會跟 iframe 搶焦點，經典的『按空白鍵沒反應』 焦點 bug 在這個設計下不存在」。

此處後來改變： 使用者接受 A 方案本身，但指出全螢幕應該由使用者自選，不能寫死在程式碼裡。 「播放永遠全螢幕」這個前提不成立，焦點問題因此依然存在，後續改以「進入播放時把焦點交給播放器、 焦點不在時明確提示」處理（見下方使用者發言）。

全螢幕應由使用者自選

使用者

我想要採用 A 方案，但是播放影片的時候一定要全螢幕，這個應該要讓使用者可以自己選——也可以不全螢幕， 就直接在那個位置上播放，也可以全螢幕播放，這應該讓使用者自己選，而不是預設寫死在程式碼裡面。

AI

同意，但誠實指出：這讓焦點問題回來了。AI 拒絕用「主文件也監聽方向鍵當備援」遮掩， 因為那樣會讓有些步驟能按、有些不能按（影音步驟需要使用者手勢，備援過不去），比壞掉更糟。 正確做法：進入播放時把焦點交給播放器；焦點不在播放器上時，畫面明確提示並可點回去，絕不無聲失效。 模式收斂成「檢視（無 script）／播放（有 script）」，全螢幕是播放模式上的一個開關，不是另一種模式。

問題 7側邊總覽：真實縮圖，還是頁碼清單？

AI
  • A. 真實縮圖 — 每頁一個零 token sandbox iframe，縮小顯示，延遲載入
  • B. 頁碼＋名稱清單 — 便宜但看不出哪頁是哪頁

建議 A：縮圖是總覽存在的全部理由。代價（每頁一個 iframe）用延遲載入（只實體化視窗附近幾頁）解決。

A

問題 8效果清單用什麼格式？

AI

位置已由 ADR-0003 邏輯決定：住在該張投影片 SVG 的 <metadata> 裡。格式：

  • A. 自訂命名空間的 XML 元素
  • B. JSON 塞進 <metadata> 文字節點

建議 A，理由是 ADR-0004（內容要 hand-readable、對 agent 友善），整份檔案維持單一語法。代價：屬性值全是字串，未來要自己轉型別。

使用者

對的，選 A 是正確的。我想要讓一個 SVG 裡面就擁有這個 SVG 的重要功能，包含這些動畫的切換， 應該都在這個 SVG 裡面能找得到。為什麼呢？今天如果我把兩個投影片對調，假設外面有一個 JSON 檔， 對調的時候不是還要改那個裡面的東西嗎？所以讓 SVG 自成一個體系是一個很好的決策， 這樣未來要再交換什麼都會比較容易。

AI

這個理由比 AI 原本給的更硬：投影片自成一體，對調兩頁不需要動任何第三個檔案。 這是「明確順序、不重編號」這條線第四次出現，會記成一份新 ADR（後續即 ADR-0008）。

問題 9音訊在投影片上是什麼？

AI
  • A. 掛在一個可見元素上（例如喇叭圖示），data-comot-media 掛在它身上
  • B. 不可見的節點 — 靜態檢視什麼都看不到
  • C. 不是元素 — 效果清單裡一項不指向元素、直接寫 src 的特例

建議 A：保住「每項效果都指向一個元素」的不變式、看不見的東西沒有把手（未來編輯時無法點選/刪除）、 agent 需要能指名它。代價：畫面上會有個喇叭圖示，播放時也在，未來再用「放映時隱藏」處理。

A

問題 10這一輪的邊界在哪？

AI

要驗證的假設：一份手寫的效果清單，加上一個對簡報內容一無所知的 runtime，就能播出 PowerPoint 等級的步驟推進，而且那份清單手寫起來不痛。

端到端路徑：執行 co-motion serve → 側邊總覽三頁縮圖 → 點頁看完整內容 → 按播放（可選內嵌或全螢幕）→ 方向鍵：元素淡入 → 影片開始播 → 音檔開始播 → 換頁。

含：多頁支援、總覽縮圖（延遲載入）、檢視／播放模式、全螢幕開關、效果清單讀取與執行、進場（先做 fade 和 appear）、媒體播放、圖片、影片、音訊。

不含：任何寫入命令、agent 參與、強調／退場／路徑家族、With/After Previous、投影片間轉場、暫停倒退、進度指示。

建議一起做：#13（HTTP Range，否則影片在部分瀏覽器可能直接拒播）、server 拒絕 Origin: null（問題 6 開放 allow-scripts 後的盲寫缺口）。

風險標記：這一輪完全沒有 agent 參與，是專案第一次；「人與 agent 共同編輯」這條主線暫停一輪。
