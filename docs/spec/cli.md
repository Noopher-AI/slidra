# slidra CLI Specification

This document is the sole normative reference for the `slidra` command-line tool. The TypeScript engine (`packages/core`/`packages/cli`) has been removed — Rust is now the only implementation, and this document is its sole source of truth. During the period the two implementations coexisted, three known gaps (`asset import`'s argv handling, `chart data set --csv -`, and the `data` shape of `effect list`) were settled, and the Rust implementation follows this spec for all three.

`.dev_docs/adr/` records the history of decisions; this document records the current and future normative facts about the command set. Where the two conflict, this document takes precedence.

**Compatibility level 2 frozen surface**: command names, the number and order of positional arguments, flag names, exit codes (0 for success, 1 for failure), and the output bytes of the three renderer commands `cat`, `ls`, and `slide render` — these must be byte-for-byte compatible with the Rust implementation. **Mutable surface**: the success `data` JSON shape of every other command (the settlement of the three known gaps is authoritative in this spec), and the Chinese-language wording of the `message` field (human-readable text, never a pattern-matchable contract).

## Addressing

- **`<presentation-id>`**: The opaque identifier returned by `open` — a 12-character base64url string encoding 9 random bytes. It cannot be decoded into any path or meaning (ADR-0004) — do not try to guess the presentation's actual filesystem location from it.
- **`<slide-path>`**: A virtual path inside the container, e.g. `slides/001.svg`, which must be listed in that presentation's `project.json` `slides` array, or in the `templates` array (templates are edited with the same set of element commands, addressed the same way). Virtual paths must not be absolute and must not contain `..` segments.
- **`<element-id>`**: An `el-` prefix followed by a 12-character base64url string (generated by the same generator as `<presentation-id>`, just with the prefix added).
- **Multi-element addressing**: Commands that accept `<element-ids>` (plural) always take a comma-separated list (e.g. `el-1,el-2,el-3`); they do not accept the flag being repeated to specify multiple values. Batch addressing still counts as **one undo step**, even though the batch touches multiple elements.

## Quoting and lists

Command-line arguments must be written as either a "bare token" (alphanumerics plus `` _ . / : = , @ + - ``, or any non-ASCII text) or a single-quoted string `'...'`. **Double quotes are not used, and backslash escaping is not used.**

- **Comma-separated lists**: `--categories Q1,Q2,Q3`, and `<element-ids>`'s `el-1,el-2` — both represent multiple values separated by commas within a single positional or flag argument, not a repeated flag.
- **`name=values` form**: `--series 'Revenue=100,120,140'`, `--color 'Revenue=#3366FF'` — everything before the `=` is the name, everything after is the value (which may itself be a comma-separated list). Values like this should almost always be wrapped in single quotes, since they can contain whitespace or non-ASCII characters in addition to the `=`.
- **Repeatable flags**: When the same flag name can appear multiple times in a single invocation (e.g. `chart axis set --right <series-name>`, `chart palette set --color 'name=#hex'`), each occurrence represents one entry rather than overwriting the previous one.
- **When quoting is mandatory**: If a value contains a comma, whitespace, or Chinese characters (including full-width punctuation), it must be wrapped in single quotes — otherwise the shell's own word-splitting rules will break it into multiple tokens before the CLI ever sees it, which is not a CLI parsing error. This is the boundary between shell quoting rules and CLI argument parsing; the CLI itself is not responsible for input the shell failed to split correctly.

## CommandResult

Each command's handler returns only this structure, and never writes to `process.stdout` or calls `process.exit` directly:

```ts
interface CommandResult<Data = unknown> {
  ok: boolean;
  data?: Data;                 // structured payload on success; absent on failure
  message: string;             // human-readable Traditional Chinese text; never contains real filesystem paths
  failureKind?: "not-found" | "failed";  // only populated by dispatch on failure
}
```

- `failureKind` has only two values: **`"not-found"`** — the requested thing has been positively proven not to exist (an unknown `<presentation-id>`, a virtual path that can't be found, an element that can't be found, etc.); **`"failed"`** — anything else (I/O errors, validation failures, malformed input, or any error subclass invented in the future that the caller hasn't seen yet). The classification rule (order matters and must not be swapped) is: if the thrown error is `SlidraNotFoundError` (or a subclass) → `not-found`; if it's any other `SlidraError` subclass → `failed`; any exception that is **not** a `SlidraError` must propagate outward and must never be converted into a `CommandResult` — that is a program bug, not a user-visible failure, and the caller must let execution keep unwinding rather than swallow it.
- The **absence** of `failureKind` (even when `ok === false`) must be read as "not proven to not exist," which maps to HTTP 500, not 404 — this is a deliberately conservative default: when a new kind of failure is invented, the default is to "fail loudly" rather than "silently be misread as a 404."
- `message` is human-readable Traditional Chinese text and **is not a contract** — its wording may change at any time. Callers must not pattern-match or branch on the string contents of `message`; it may only be shown to a human. `message` never contains a real filesystem path (whether on success or failure).
- Exit code: always `0` on success, always `1` on failure — there is no third exit code.

## Terminal output

For commands with no registered renderer (84 of the 87 commands): the default output is "status line + JSON" — first a line of `message` is printed, then, if `data !== undefined`, a second line of `JSON.stringify(data, null, 2)` is printed; when `data` is `undefined`, only the status line is printed and there is no second line. On failure, `message` is printed to stderr and no JSON is printed.

For the three commands with a renderer (`cat`, `ls`, `slide render`): the output rules are described in the next section.

**Downstream pipe closing early** (e.g. `slidra cat <id> <path> | head`): for these one-shot commands, an EPIPE is treated as a normal termination — the process calls `process.exit(0)` and this is not treated as an error. `export`/`serve` **do not** follow this rule — if `export` encounters an EPIPE partway through writing output it calls `process.exit(0)`, which would misreport an incomplete export as successful, so this handling is deliberately not installed there.

## Renderer commands: `cat`, `ls`, `slide render`

Only these three commands bypass the default "status line + JSON" output and instead print the raw bytes corresponding to `data`:

| Command | Output rule |
|---|---|
| `cat` | `data.content` is written to stdout verbatim, **with no extra newline and no wrapping of any kind** (equivalent to Unix `cat`: the file's complete raw bytes, no more, no less) |
| `ls` | `data.entries.map(e => e + "\n").join("")` — one entry per line, with no total count and no JSON wrapping (equivalent to the simplest form of Unix `ls`) |
| `slide render` | Exactly the same renderer as `cat` (`data.content` output verbatim); `slide render` is the "display-time" version of `cat`: before the content is read out, dynamic text such as `{{ slide_number }}`/`{{ slide_total }}`/`{{ presentation_name }}` is substituted; otherwise the byte-level output rules are identical to `cat` |

The remaining 78 commands always have `render: null` and use the default output described in the previous section.

## --json (global flag)

`--json` is a global flag settled in this spec and implemented by the Rust entry point.

- Position: it may only appear after the command name (e.g. `slidra cat <id> <path> --json`); it does not affect the parsing order of any command's own positional arguments and flags.
- Output: a single line of compact (unindented) JSON followed by a newline, with the field order fixed as `ok, data, message, failureKind`.
- Commands with a renderer also always return JSON under `--json`, rather than the renderer's raw-byte output; fields such as `data.content`, which are normally raw text/bytes, are encoded as **base64 of the raw bytes** under `--json` (since a JSON string cannot safely carry arbitrary binary content).
- `cat --json` is the only form allowed to accept **multiple** `<path>` arguments: `data` becomes an array `[{ path, content }]`, in the same order the paths were given on argv; **without** `--json`, `cat` still only accepts a single path and outputs the raw bytes directly (this is compatibility-level-2 frozen behavior, and is not changed by the multi-path need).
- On failure, JSON is still printed (`ok: false`, including `failureKind`, without `data`), and the exit code is still `1`.
- `slidra serve` is always treated as if `--json` were passed (its caller is a program, not a terminal user, so it has no need for human-readable status-line/renderer output).

## "`-`" means standard input

The spec defines a set of "stdin-substitutable" flags. At the entry-point layer (`main` in `bin.ts`, or the corresponding location in `main.rs` for the Rust version), **before** calling `dispatch`, a check is made: if a substitutable flag's value is exactly the literal string `"-"`, the full contents of stdin (UTF-8) are read, and that field is rewritten from a "path field" into a same-named field of a different type, `*Text`, before being passed to `dispatch`. `parseArgv` itself is a pure function — it does not read stdin and does not perform this substitution. The substitution must happen at the entry-point layer, because `serve` calls `registry.dispatch` directly, completely bypassing `parseArgv`; if the substitution logic lived at the argv layer, this substitution would never happen on the `serve` path.

Currently the **only** substitutable flag is `chart data set`'s `--csv`. `slidra serve` has no terminal stdin to read — if the handler receives the literal, un-substituted value `"-"` (i.e., it was called directly through `serve`, bypassing the entry-point substitution), it must explicitly return a failure and must not treat `"-"` as a filename to read.

## Environment variables

- **`SLIDRA_HOME`**: The workspace root directory outside of `.slidra`, defaulting to `~/.slidra`. This environment variable is re-read on every invocation and is never cached — changing it during the lifetime of the same process takes effect on the next invocation. See `workspace.md` for layout details.
- **`SLIDRA_BIN`**: Before the Rust entry point execs Node (to run `serve`/`export`), it sets its own absolute path into this environment variable. Anywhere on the Node side that needs to spawn the `slidra` command again must use the **same binary** pointed to by this environment variable; if it isn't set, that is an outright error, and there is **no fallback to searching PATH for `slidra`** (the architectural principle of "one binary, one truth": it must never be possible for the Node side to accidentally spawn a different, unrelated `slidra` binary elsewhere on the system).
- **`SLIDRA_ID_SEED`**: When set, the id generators (`<presentation-id>`/`<element-id>`) switch to deterministic output, for test use only; the literal id format (`el-` prefix + 12-character base64url) does not change as a result. **The actual algorithm behind the deterministic sequence is not part of this spec's contract** — it is left to the implementing crate; the only required external behavior is "setting this environment variable makes the output deterministic, and the format is unchanged."

## Undo semantics

- **One operation = one command = one undo step** (ADR-0002). Batch addressing (a single command that touches multiple `<element-id>`s at once) still counts as one step, even though it affects multiple elements internally.
- **Read-only commands do not enter history**: `cat`, `ls`, `effect list`, `template list`, `comment list` — these commands do not write to disk, do not create a history group, and do not produce an undo step.
- **One known exception**: `presentation canvas set` does write to `project.json` (changing the canvas dimensions), but is deliberately designed to **not consume any undo step** — this is the one exception to the "one operation, one undo step" rule, on the grounds that canvas size is a presentation-level property rather than a piece of step-revertible content editing.
- The actual storage location and on-disk format of history is described in [the workspace specification](workspace.md).

## Entry points that bypass the registry: `serve` and `export`

The `serve`/`export` subcommands **are not counted among the 88 commands** and do not use the command-entry format described below. They are branched off at the binary entry point itself (`packages/server/bin/slidra-node.js`: when `argv[0] === "serve"` or `"export"`, the `runServeCli`/`runExportCli` functions from `@slidra/server` are dynamically loaded and called directly), entirely bypassing `parseArgv` and `CommandRegistry`.

Behavior of the Rust entry point: upon detecting `serve`/`export`, it first writes its own absolute path into `SLIDRA_BIN`, then `exec`s Node to run the corresponding CLI entry point in `@slidra/server`, passing argv, stdin, stdout, stderr, and exit code through byte-for-byte.

## Command-entry format description

Below, every command entry uses `` ## `<command-name>` `` as its heading — **an H2 with the full command name wrapped in backticks, and nothing else on that line**. This is the only H2 style in this document that is allowed to begin with a backtick; every other H2 in this document (the general sections above, and the appendices below) never begins with a backtick. This rule is also the sole format that the subset-check script (`scripts/check-reference-subset.mjs`) and the `cli_md_lists_exactly_the_88_rust_dispatched_commands` test in `crates/slidra/tests/cli_golden.rs` rely on when parsing the command list (the extraction regex is fixed as `` /^## `(.+)`$/gm ``): this is precisely why `serve`/`export` cannot use this heading format — doing so would make the extracted command count 90, which would not match the 88 commands registered in Rust.

Every command entry has exactly five subsections, always in this order:

1. **Syntax**: a single code block line, with positional arguments in `<angle brackets>`, optional flags in `[square brackets]`, and repeatable flags annotated "(repeatable)".
2. **Parameters**: each positional argument and flag listed individually, with its type and whether it's required; whenever the value domain is a fixed set, the entire set is listed, with nothing omitted.
3. **Success `data`**: a JSON code block showing the actual shape (not a `{...}` placeholder); commands with no payload are written as `{}`. For `cat`, `ls`, and `slide render`, the byte-level renderer output rules are additionally described (already covered above in the "Renderer commands" section — the entry does not repeat that whole section, only references or briefly summarizes it).
4. **Error cases**: a table with at least one row, each row being "condition → `failureKind`".
5. **Example**: one line with a command that can be copy-pasted and run directly.

The following 88 commands are listed in the **registration order** of `CommandRegistry.names()` (not alphabetical order):
## `new`

**Syntax**

```
slidra new <path> [--name <name>]
```

**Parameters**

- `path`: string, required. The local filesystem path of the `.slidra` file to create (a new file, not the identifier of an existing presentation — `new` is one of the only commands that operates directly on a real filesystem path rather than through a `<presentation-id>`, because the target it creates isn't yet an "opened" presentation to begin with).
- `--name`: string, optional. The presentation's display name, written to `project.json.name`; defaults to "New Presentation" if omitted.

The presentation created this way has **no slides at all** (`project.json.slides` is an empty array), and contains only `project.json`, embedded fonts, and their license text (ADR-0018): the first slide is produced afterward by the author or an agent using `slide add` or `/slidra-plan` → `/slidra-build` — no undesigned placeholder page is added in advance.

**Success `data`**

```json
{}
```

**Error cases**

| Condition | `failureKind` |
|---|---|
| The directory containing `path` is not writable, or the disk write fails | `failed` |

**Example**

```
slidra new ./deck.slidra --name 'My Presentation'
```

## `open`

**Syntax**

```
slidra open <path>
```

**Parameters**

- `path`: string, required. The local filesystem path of an existing `.slidra` file.

`open` operates on `path` **in place** — there is no separate work directory or copy (`spec/rfcs/0001-sqlite-container-format.md`). If `path` is still a legacy ZIP container (`formatVersion` 1 through 4), it is migrated to the SQLite container format first, as a single atomic same-directory rename; a SQLite deck already at the crate's current version is opened unchanged. From this point on, `path` itself IS the presentation's content — editing commands write directly into it, and `pack`ing back to the same path is a no-op copy that only updates the "saved" bookkeeping.

**Success `data`**

```json
{ "id": "AbCdEfGhIjKl" }
```

`id` is a 12-character base64url opaque identifier (see the "element id format" section of `slidra-format.md`; `<presentation-id>` uses the same generator), and is the first positional argument of every subsequent command. Opening the same `path` more than once mints a distinct id each time; every id minted this way shares the exact same underlying file, so an edit made through one id is immediately visible through any other id opened against that same path.

**Error cases**

| Condition | `failureKind` |
|---|---|
| The file at `path` does not exist, or fails to read | `failed` |
| `path` points to something that is not a file (e.g. a directory) | `failed` |
| The file's header bytes match neither a legacy ZIP nor a SQLite container | `failed` |
| A legacy ZIP's decompressed content is missing a parseable `project.json`, or `project.json`'s format does not match the spec (see `slidra-format.md`) | `failed` |
| The container's stored format version is greater than the maximum version this build supports | `failed` |
| An error occurs while registering the presentation, whether a disk error or an error in the registry file itself (`projects.json`) | `failed` |

> All of these conditions are currently classified as `failed`, not `not-found` — `open`'s input is a local filesystem path, not "an identifier that may or may not exist," so there is no semantic case of "a known registered thing was not found"; a corrupted archive or non-conforming content both fall under "this request cannot be completed" rather than "positive proof that a known identifier does not exist."

**Example**

```
slidra open ./deck.slidra
```

## `pack`

**Syntax**

```
slidra pack <presentation-id> <path>
```

**Parameters**

- `presentation-id`: string, required, the identifier of an opened presentation.
- `path`: string, required, the local filesystem path of the output `.slidra` file.

When `path` is the presentation's own deck file (the one `open` operates on in place), `pack` copies nothing — the content is already there — and simply updates `~/.slidra/projects.json`'s `savedAt` bookkeeping when `path` also matches the presentation's remembered source path (see `workspace.md`). Any other `path` is a plain file copy of the deck's current bytes (staged then renamed, overwriting whatever was there); it additionally marks the presentation "saved" only when `path` matches that same remembered source.

**Success `data`**

```json
{}
```

**Error cases**

| Condition | `failureKind` |
|---|---|
| `presentation-id` does not exist | `not-found` |
| The directory containing `path` is not writable, or the disk write fails | `failed` |

**Example**

```
slidra pack pres-abc123 ./deck.slidra
```

## `extract`

**Syntax**

```
slidra extract <id-or-path> <dir>
```

**Parameters**

- `id-or-path`: string, required. Either an already-`open`ed presentation's id, or a `.slidra` filesystem path (legacy ZIP or SQLite) not yet opened.
- `dir`: string, required. A local filesystem directory to write the deck's entire virtual filesystem into, as plain real files — every empty directory in the deck (e.g. a freshly `new`ed deck's `assets/`) is reproduced too, not just files.

`extract` is read-only against the source: given a filesystem path, it never migrates or registers anything, so it is safe to run against a `.slidra` an author does not want touched — the escape hatch for getting back to "just files on disk" without any tool that understands the SQLite container format (`spec/rfcs/0001-sqlite-container-format.md` decision 6).

**Success `data`**

```json
{}
```

**Error cases**

| Condition | `failureKind` |
|---|---|
| `id-or-path` resolves to neither a registered id nor a readable file | `failed` |
| `dir` already exists and is not empty | `failed` |
| `dir` exists but is not a directory | `failed` |
| The disk write fails | `failed` |

**Example**

```
slidra extract pres-abc123 ./extracted
slidra extract ./deck.slidra ./extracted
```

## `cat`

**Syntax**

```
slidra cat <presentation-id> <path>
```

**Parameters**

- `presentation-id`: string, required.
- `path`: string, required, a virtual path inside the container (e.g. `project.json`, `slides/001.svg`, `assets/photo-1.png`), not a local filesystem path.

**Success `data`**

```json
{ "content": "<the file's complete raw content>" }
```

`content` is text content (read as UTF-8); see the "Renderer commands" section for the terminal output rules — by default, `data.content` is printed to stdout verbatim, with no added newline, no `message`, and no JSON wrapping. Only when combined with the global `--json` flag is the entire `CommandResult` printed as JSON instead, with `data.content` encoded as base64 (see the general "`--json`" section).

**Error cases**

| Condition | `failureKind` |
|---|---|
| `presentation-id` does not exist | `not-found` |
| `path` does not correspond to any file or directory | `not-found` |
| `path` corresponds to a directory rather than a file | `not-found` |

**Example**

```
slidra cat pres-abc123 slides/001.svg
```

## `ls`

**Syntax**

```
slidra ls <presentation-id> [path]
```

**Parameters**

- `presentation-id`: string, required.
- `path`: string, optional, a virtual directory path inside the container; when omitted, lists the top level (`project.json`, `slides/`, `assets/`, `fonts/`, and `templates/` when it optionally exists).

**Success `data`**

```json
{ "entries": ["project.json", "slides", "assets", "fonts"] }
```

`entries` is sorted lexicographically by the actual names in the directory, with no distinction between files and subdirectories. See "Renderer commands" for the terminal output rules: by default, each entry is printed on its own line (`entries.map(e => e + "\n").join("")`), with no total count and no JSON wrapping.

**Error cases**

| Condition | `failureKind` |
|---|---|
| `presentation-id` does not exist | `not-found` |
| `path` does not correspond to any directory (including the case where it points to a file rather than a directory) | `not-found` |

**Example**

```
slidra ls pres-abc123
slidra ls pres-abc123 slides
```
## `text set`

**Syntax**

```
slidra text set <presentation-id> <slide-path> <element-id> <new-text> [--force]
```

**Parameters**

- `presentation-id`: string, required. The identifier of the presentation to modify.
- `slide-path`: string, required. A virtual path (e.g. `slides/001.svg`); it may be a slide listed in `project.json`'s `slides` list, **or a template listed in the `templates` list** (`text set` is not restricted to slides that have already been inserted).
- `element-id`: string, required. The id of the element whose text is to be modified.
- `new-text`: string, required, but **an empty string `''` is allowed** — an empty string is a valid value, meaning "clear this element's text content," and is not rejected as a "missing argument" (only completely omitting this position counts as missing). Multiple lines separated by `\n` are each converted into a separate `<tspan>` line.
- `--force`: boolean flag, optional. May only appear at the fixed position right after `new-text` (the 5th positional argument); appearing anywhere else, or any other extra argument, is treated as an unknown parameter and reported as an error. Used to bypass "locked element" protection (ADR-0013) — when the target element carries `data-slidra-lock="true"`, `text set` normally refuses to modify it, and `--force` is required to modify it; the lock status itself is not cleared or changed.

**Success `data`**

```json
{}
```

**Error cases**

| Condition | `failureKind` |
|---|---|
| `presentation-id` does not exist | `not-found` |
| `slide-path` does not correspond to any file (including the case where it points to a directory) | `not-found` |
| `slide-path` is not in that presentation's `slides` or `templates` list | `failed` |
| `new-text` contains characters not allowed by XML 1.0 (e.g. control characters) | `failed` |
| `element-id` cannot be found on that slide | `failed` |
| The target element is a locked layout skeleton element, and `--force` was not given | `failed` |
| The target element is not a text-bearing element, or that element has no text content to replace | `failed` |
| The target is a text box, but its `data-slidra-text-width` is not a valid positive number, or the declared font is not embedded in the presentation (the data is corrupted) | `failed` |

**Example**

```
slidra text set pres-abc123 slides/001.svg el-title 'New title text'
slidra text set pres-abc123 slides/001.svg el-locked '' --force
```

## `text style set`

**Syntax**

```
slidra text style set <presentation-id> <slide-path> <element-id> --range <start>:<end> [--font-weight <value>] [--font-style <value>] [--force]
```

**Parameters**

- `presentation-id`: string, required.
- `slide-path`: string, required, same as `text set` — may be a registered slide or a template.
- `element-id`: string, required, must be a **text box** (a container carrying `data-slidra-text-width`), not a plain `<text>` element.
- `--range <start>:<end>`: required, in the fixed format "non-negative integer:non-negative integer", with `start` required to be less than `end` (a half-open interval `[start, end)`, in units of characters, against the text box's content string). A malformed format or reversed bounds is reported as an error directly at the command-parsing stage.
- `--font-weight`: optional string. Valid values are `normal`, `bold`, or a multiple of 100 (`100`–`900`). `normal` **clears** the `font-weight` style over that range (rather than setting it to normal); any other valid value sets that style; omitting the flag entirely leaves the existing style over that range unchanged.
- `--font-style`: optional string. Valid values are `normal` (clears the italic style) or `italic` (sets italic); omitting it leaves it unchanged.
- At least one of `--font-weight` and `--font-style` must be provided, otherwise this is reported as an error at the command-parsing stage (execution never begins).
- `--force`: boolean flag, may appear anywhere among the arguments. Same as `text set`, used to bypass locked-element protection.

**Success `data`**

```json
{ "runs": 3 }
```

`runs` is the total number of runs the text box's content is split into by style boundaries after the style is applied.

**Error cases**

| Condition | `failureKind` |
|---|---|
| `presentation-id` does not exist | `not-found` |
| `slide-path` does not correspond to any file | `not-found` |
| `slide-path` is not in the `slides` or `templates` list | `failed` |
| `--font-weight`'s value is not `normal`, `bold`, or a multiple of 100 between 100 and 900 | `failed` |
| `--font-style`'s value is not `normal` or `italic` | `failed` |
| `element-id` cannot be found on that slide | `failed` |
| `element-id` exists but is not a text box (no `data-slidra-text-width`) | `failed` |
| The target container is not a valid text-box content consisting of a single `<text>` child, or that `<text>` has no content | `failed` |
| `--range`'s `end` exceeds the current character length of the text box's content | `failed` |
| The target element is a locked layout skeleton element, and `--force` was not given | `failed` |

**Example**

```
slidra text style set pres-abc123 slides/001.svg el-body --range 0:5 --font-weight bold
slidra text style set pres-abc123 slides/001.svg el-body --range 5:12 --font-style italic --force
```

## `text list set`

**Syntax**

```
slidra text list set <presentation-id> <slide-path> <element-id> --paragraph <n> --kind bullet|number|none [--force]
```

**Parameters**

- `presentation-id`: string, required.
- `slide-path`: string, required, same as `text set` — may be a registered slide or a template.
- `element-id`: string, required, must be a text box.
- `--paragraph`: required, non-negative integer (0-based), corresponding to the paragraph index of the text box's content when split on `"\n"`; a malformed non-negative-integer format is reported as an error at the command-parsing stage.
- `--kind`: required, one of the fixed set `bullet`, `number`, `none`; a value outside this set is reported as an error at the command-parsing stage.
- `--force`: boolean flag, may appear anywhere among the arguments, bypasses locked-element protection.

**Success `data`**

## `convert`

**Syntax**

```
slidra convert <presentation-id>
```

**Parameters**

- `presentation-id`: string, required. The identifier of the presentation to convert. There is no per-slide or dry-run form — this command processes every slide in the entire presentation in one go, all or nothing.

**Success `data`**

```json
{
  "slides": [
    { "slidePath": "slides/001.svg", "changed": true, "wrapped": 2 }
  ]
}
```

The `slides` array covers every slide listed in `project.json.slides`, in original order; `changed` indicates whether that slide's bytes were altered by the conversion; `wrapped` is the number of containers (`<g id="el-…">`) added to that slide by the conversion.

**Error cases**

| Scenario | `failureKind` |
|---|---|
| `presentation-id` does not exist | `not-found` |
| Any slide's content cannot be normalized (e.g. its structure is severely corrupted and the normalization logic itself throws) | `failed` |
| A disk error occurs while writing a slide | `failed` |

> Errors during the read phase (before normalization) and the write phase are both classified as `failed`. The write phase is specifically designed to avoid leaving partial results: all slides are first fully read and normalized, and if even one fails to normalize, not a single byte is written. Once the write phase has actually begun, if writing a given slide fails, the other slides already written are restored to their original content on a best-effort basis, and the error message honestly reports whether the restoration fully succeeded, rather than falsely claiming that the whole presentation was left unmodified when in fact an exception occurred.

**Example**

```
slidra convert pres-abc123
```

## `element paste`

**Syntax**

```
slidra element paste <presentation-id> <slide-path> [--dx n] [--dy n] [--svg-file path]
```

**Parameters**

- `presentation-id`: required, positional.
- `slide-path`: required, positional, the paste destination (may be a different slide than the copy source).
- `--dx`: optional, number, default `0`; an additional offset applied to each new element's own container after pasting.
- `--dy`: optional, number, default `0`.
- `--svg-file`: optional, local file path, whose contents must be an `<svg>` string in the system clipboard exchange format (a CLI-only flag; failing to read the file raises an error). When `--svg-file` is given, its content is parsed and pasted directly, without reading from or writing to that presentation's internal clipboard file at all; when it is omitted, the internal clipboard file previously written by `element copy`/`element cut` for that presentation is read instead.

**Success `data`**

```json
{ "elementIds": ["el-a", "el-b"] }
```

`elementIds` is the new top-level element id corresponding to each clipboard item after pasting (in the clipboard's original order, never including descendant ids) — every container id (including descendants) is regenerated on paste, and is also substituted into the `target` field of any effect entries.

**Error cases**

| Case | `failureKind` |
|---|---|
| `presentation-id` does not exist | `not-found` |
| The file at `slide-path` does not exist | `not-found` |
| `slide-path` exists but is not listed in the slides/templates list in `project.json` | `failed` |
| The local file specified by `--svg-file` cannot be read | `failed` |
| `--svg-file` was not given and that presentation's internal clipboard file does not exist (nothing has been copied/cut yet, or it was cleared some other way) | `failed` |
| The internal clipboard file exists but fails to read (an I/O error other than "file not found") | `failed` |
| The internal clipboard file's content is not valid JSON | `failed` |
| The content given via `--svg-file` is not a valid slidra element clipboard format (missing identifying marker, or unparseable) | `failed` |
| The clipboard content is empty (no elements to paste) | `failed` |
| The clipboard content fails the three-layer validation (structure, single root node, attribute/value allowlist — ADR-0010, see `sanitizeClipboardMarkup`) | `failed` |

**Example**

```
slidra element paste pres-123 slides/2.svg --dx 20 --dy 20
```

(The `--svg` system-clipboard-string input exists as a field on the `ElementPasteInput` type, but the CLI's argv layer currently only exposes `--svg-file`, not a corresponding `--svg` flag; the content read from `--svg-file` is used as that field's value.)

## `plan set`

**Syntax**

```
slidra plan set <presentation-id> <name> <content> [--force]
```

**Parameters**

- `presentation-id`: string, required.
- `name`: positional argument, required, must be either `outline` (writes `plan/outline.md`) or `design-spec` (writes `plan/design-spec.md`).
- `content`: positional argument, required, the full text of the file. It must begin with a ```` ```json ```` fence (the machine-readable segment), followed by any Markdown prose. Before writing, the JSON segment is parsed and validated: `outline` must have `status` (`draft` | `confirmed`), `mode` (`pyramid` | `narrative` | `instructional` | `showcase` | `briefing`), a non-empty `pages` array (each item has `n` incrementing consecutively from 1, a required `relationship` in order|link|parent|membership|contrast|overlap|none, a required `rhythm` in anchor|dense|breathing, a required `title`, an optional `type` in cover|section|bullets|compare|number|closing, and an optional `blueprint` (a non-empty string `shape`, plus non-negative integers `nodes`/`steps`)), and an optional `questions` array (each question has a unique `id`, a `question`, a `recommended` that must match the `value` of one of 2-4 `options`, and optional `note` and `free_text`); `design-spec` must have `density` (`presentation` | `balanced` | `text`), `palette` (seven roles — `background`/`secondary_bg`/`primary`/`accent`/`secondary_accent`/`text`/`muted` — all as uppercase `#RRGGBB`), and `type_scale` (nine roles — `cover`/`section`/`number`/`claim`/`title`/`subtitle`/`body`/`column`/`caption` — all positive numbers). If any item fails validation, the write is rejected and nothing is persisted. Plan files are not slide content, and **do not enter the undo history** (ADR-0018).
- `--force`: optional, may only appear after `content`. Bypasses the "confirmed plan" guard described below; all other validation still runs.

**What a confirmed plan is allowed to change**

When the existing `plan/outline.md` has `status` equal to `confirmed` (a `draft` plan is unrestricted), this write is compared against the existing content, and the following changes are rejected unless `--force` is given:

| Rejected | Why |
|---|---|
| Changing `status` from `confirmed` back to `draft` | Would reopen the author's confirmation gate and disable `validate`'s `blueprint.required` |
| Changing `mode`/`animation`/`background` | These are the three questions the author already answered at the gate |
| Reducing the number of `pages` | Deleting pages |
| Changing `relationship`/`rhythm`/`title` of an existing page | Same reasoning — the page skeleton the author already confirmed |
| Changing the `blueprint` of page `n` when it **already has** one and `n ≤ current slide count` | Composition comes before the page. Once a page is drawn, changing its composition numbers would just be retroactively editing an answer to match work done after the fact |

Allowed: writing a `blueprint` for a page for the first time, changing the `blueprint` of a page not yet drawn (`n > current slide count`), changing the `type` field, and appending new pages at the end. Pages and slides are matched by position, consistent with `validate`. When the existing file itself cannot be parsed, no comparison is performed — that write is treated as a repair path.

**Success `data`**

```json
{ "path": "plan/outline.md" }
```

**Error cases**

| Case | `failureKind` |
|---|---|
| `presentation-id` does not exist | `not-found` |
| `name` is neither `outline` nor `design-spec` | `failed` |
| `content` is missing the ```` ```json ```` fence, the JSON cannot be parsed, or any field violates the rules above | `failed` |
| A confirmed plan changes a protected field without `--force` | `failed` |

**Example**

```
slidra plan set pres-1 outline '```json
{ "status": "draft", "mode": "pyramid", "pages": [ { "n": 1, "type": "cover", "rhythm": "anchor", "title": "Cover" } ] }
```

## Page 1
The cover'\''s claim and how the audience changes.'
```

## `validate`

**Syntax**

```
slidra validate <presentation-id> [slide-path]
```

**Parameters**

- `presentation-id`: string, required.
- `slide-path`: positional argument, optional, must be in the `slides` list; if omitted, the entire presentation is validated (including cross-page rules).

The rules are hard-coded in Rust, with thresholds selected according to the `density` in `plan/design-spec.md` (`presentation`: title ≤ 24 characters, bullet ≤ 32 characters and ≤ 2 lines, 2-7 bullets, page total ≤ 1000 characters; `balanced`: 32/48/3 lines/2-8/1400; `text`: 40/64/4 lines/2-9/2000; the thresholds are deliberately loose — layouts that genuinely don't fit are caught by `geometry.*`, these rules only catch the obviously excessive cases; character counts exclude whitespace, and `{{ … }}` dynamic-text placeholders count as 0 characters), and the color palette, type scale, `shape_language` (optional, one of `plain`/`swiss-minimal`/`soft-rounded`/`glass`/`paper-cut`/`ink-wash`/`chalkboard`/`sketch-notes`/`brutalist`/`data-dense`, defaulting to `plain` when omitted; it only describes shape behavior, not color), and `layout` anchors (`side_margin` / `bottom_margin` / `footer_margin` / `gutter` / `spacing`, the whole group may be omitted, in which case they default to 80/72/16/24/`[8,16,24,40,64]` respectively; if given, they must be valid numbers) are also read from it — the safe-area boundaries for `geometry.*` are derived from the first three of these, falling back to the same defaults when there is no design-spec. Page count, relationships, page types, and rhythm are read from `plan/outline.md` (every page must have a required `relationship` in order/link/parent/membership/contrast/overlap/none; `type` is optional, and `roster.page-type` and `structure.template` are only validated when it is present). `rhythm.repeated-shape` (requires an outline): flags an error when two adjacent pages share the same `relationship`, the same `blueprint.shape`, and the same `blueprint.nodes`. `blueprint.required` (requires an outline): when `status` is `confirmed`, every page must have a `blueprint`. `role.required` (requires an outline): a page whose `relationship` is not `none` must have at least one element with `data-slidra-role="node"`. `role.garnish-animated` (no plan required): an element with `data-slidra-role="garnish"` must not be the `target` of any `<slidra:effect>`. `roster.relationship-variety` (requires an outline): for presentations with 4 or more pages, no single `relationship` may account for more than half of the total page count. When there is no plan file, only the rules that don't require a plan are run (`geometry.*`, `structure.background`, `structure.notes`, `taboo.*`), and `message` is annotated with a note that no `plan/` plan file was found, so only geometry and structure were checked. The fixed set of `rule` values is: `text.title-length`, `text.bullet-length`, `text.bullet-lines`, `text.bullet-count`, `text.page-total`, `focus.single-title`, `geometry.right-overflow`, `geometry.bottom-overflow`, `geometry.text-overlap`, `style.font-size`, `style.text-fill`, `style.shape-fill`, `structure.background`, `structure.notes`, `structure.template`, `roster.page-count`, `roster.page-type`, `rhythm.breathing-cards`, `motion.transition`, `motion.enter`, `structure.scrim`, `structure.background-image`, `role.garnish-meaning`, `role.spine-count`, `role.edge-endpoints`, `role.node-label`, `blueprint.required`, `blueprint.nodes`, `blueprint.steps`, `role.required`, `role.garnish-animated`, `rhythm.repeated-shape`, `roster.relationship-variety`, `taboo.thank-you`, `taboo.duplicate-cover`, `taboo.stroke`. A text box whose font size is ≤ the `caption` entry in the type scale (a footer) is allowed to extend down to canvas-bottom − 16·k; all other text boxes must stay above canvas-bottom − 72·k. `structure.scrim` (requires a design-spec): when a page has an element with `data-slidra-role="background"`, every text box (except a footer at ≤ caption size and large text at ≥ claim size) must fall entirely within a rect that precedes it in document order, whose fill is `background` or `secondary_bg`, and whose opacity is ≥ 0.6. The background-image element itself is not constrained by any rule. `blueprint.*` (requires an outline): each page in `plan/outline.md` may optionally carry a `blueprint` object (a non-empty string `shape`, plus non-negative integers `nodes` and `steps`; once given, it must be complete). For a page with a blueprint, the number of elements with `data-slidra-role="node"` must equal `nodes`, and the number of on-click enter effects must equal `steps`. `role.*` (no plan required): an element may optionally declare `data-slidra-role` (`field`/`node`/`spine`/`edge`/`label`/`garnish`, plus `background`, which the CLI assigns itself); pages with no declared roles are validated as before, but once roles are declared they must be self-consistent — a `garnish` must not be a text box, a page may have at most one `spine`, having an `edge` requires at least two `node`s, and the number of `label`s must be no fewer than the number of `node`s used as color blocks. Role declarations on a text box are carried onto the normalized element by `slide add --svg`/`slide set --svg`; a role not on the list is rejected outright. `structure.background-image` (requires an outline): when `background` in `plan/outline.md` is `on` (the default), every page must have an element with `data-slidra-role="background"`.

**Success `data`**

```json
{ "checked": 6, "errors": [ { "slide": "slides/002.svg", "element": "el-abc", "rule": "text.bullet-length", "actual": "37 characters", "limit": "≤ 32 characters", "message": "Page 2, bullet 3 has 37 characters, limit is 32" } ] }

## `effect add`

**Syntax**

```
slidra effect add <presentation-id> <slide-path> <element-id>[,<element-id>...] --family <enter|emphasis|exit|path|media> --effect <effect-name> [--start <on-click|with-previous|after-previous>] [--duration <seconds>] [--delay <seconds>] [--d <svg-path-data>] [--index <n>]
```

**Parameters**

- `presentation-id`: string, required.
- `slide-path`: string, required. May point to either a regular slide or a template (a `templates/*.svg` created by `template add`) — under the hood it only requires the path to exist in either `slides` or `templates` in `project.json`; it is not restricted to slides.
- `element-id`: comma-separated list, required, at least one. Each id is checked for existence one by one before writing; if any one does not exist, the entire command fails and nothing is written (all-or-nothing). An empty string appearing in the list (e.g. `"a,,b"` or a trailing comma) is rejected directly at the argv-parsing layer and never reaches the `not-found` check here.
- `--family`: required, one of the fixed set `enter | emphasis | exit | path | media`. This value is set-checked at the argv-parsing layer, so an invalid value terminates immediately with an unstructured error (exit code 1, no `failureKind`) and never reaches the error-case table below.
- `--effect`: required, string. The set of legal values depends on `--family` (not checked at the argv layer — checked by the handler): `enter` → `appear|fade|fly-up|fly-left|zoom`; `emphasis` → `pulse|spin|grow`; `exit` → `disappear|fade-out|zoom-out`; `path` → `path`; `media` → `play|pause`.
- `--start`: optional, one of the fixed set `on-click | with-previous | after-previous` (set-checked at the argv layer, same as `--family`). When omitted, the first `element-id` in the list uses `"on-click"`; if there are multiple `element-id`s, every one after the first is forced to `"with-previous"` (regardless of what `--start` was given) — a single `effect add` call only applies your specified `--start` to the first element.
- `--duration`: optional, number (seconds), must be `>= 0` and finite. When omitted, the default depends on `--family`: `0` for `media`, `0.6` for everything else.
- `--delay`: optional, number (seconds), must be `>= 0` and finite. Defaults to `0` when omitted.
- `--d`: optional, string (SVG path data). Required when `--family` is `path` (missing it is an error); for other families, if given, it is preserved verbatim but unused.
- `--index`: optional, 1-based integer insertion position. When omitted, it defaults to "append to the end of the list" (equivalent to the current effect count + 1); the range must fall between `1` and "current effect count + 1" inclusive, otherwise it is an error. If the slide has no existing effect list at all, the "current effect count" is treated as 0 (so the only valid value is 1).

**Success `data`**

```json
{}
```

**Error cases**

| Case | `failureKind` |
|---|---|
| `presentation-id` does not exist | `not-found` |
| `slide-path` does not exist (the virtual filesystem cannot find this file) | `not-found` |
| `slide-path` exists but is in neither the `slides` nor `templates` list | `failed` |
| Any id in the `element-id` list cannot be found on this slide (matched against the entire slide, not limited to a specific container) | `not-found` |
| The `--effect` value is not in the set allowed for `--family` | `failed` |
| `--family` is `path` but `--d` was not given | `failed` |
| `--duration` or `--delay` is negative or non-finite | `failed` |
| `--index` is outside the range `1`..`current effect count + 1` | `failed` |

**Uncertain / open items (not part of the formatted table above, included as additional notes)**: The core write logic (`addEffects`/`insertEffectItems`) does not check the structural invariant that "the first item in an effect list must have `start` equal to `on-click`" — if you insert a new item with `--start with-previous` before the existing first item (or use `--index 1` with a non-`on-click` value), the command succeeds and writes without error, and the problem only surfaces later when something calls `deriveSteps` (used by playback/export paths such as `packages/web/src/player-plan.ts`). The CLI layer itself performs no such check, so this behavior is not listed in the error-case table above.

**Example**

```
slidra effect add pres-1 slides/001.svg el-a,el-b --family enter --effect fade --duration 0.8

## `effect list`

**Syntax**

```
slidra effect list <presentation-id> <slide-path>
```

**Parameters**

- `presentation-id`: string, required.
- `slide-path`: string, required, must be listed in the presentation's `project.json` `slides` list (templates are not applicable).

**Success `data`**

```json
{
  "effects": [
    { "target": "el-p5-b", "family": "enter", "effect": "fade",
      "start": "on-click", "duration": 0.6, "delay": 0, "index": 1 }
  ],
  "steps": [
    { "effects": [
        { "target": "el-p5-b", "family": "enter", "effect": "fade",
          "start": "on-click", "duration": 0.6, "delay": 0, "index": 1 }
      ] }
  ],
  "transition": {
    "enter": { "effect": "none", "duration": 0.6 },
    "exit":  { "effect": "none", "duration": 0.5 }
  }
}
```

- `effects[]`: the full effect list for this slide, in playback order (equivalent to XML document order). `index` is **1-based** (`effect move`/`set`/`remove` also take a 1-based `index`, consistently); the `d` field only appears when `family === "path"` — for other families, even if the attribute exists in the XML, it is neither validated nor used (but is preserved verbatim on write).
- `steps[]`: **derived** from `effects[]`, not stored as independent data in the file (ADR-0008) — an item with `start === "on-click"` opens a new step, while `with-previous`/`after-previous` merge into the current step. An empty effect list returns `steps: []`. **The objects inside `steps[].effects[]` are the same shapes with the same 1-based `index` as the top-level `effects[]`** — they are not re-numbered as sub-list indices.
- `transition`: **always present**, never `null` and never omitted. When this slide has no `<slidra:transition>`, the returned value is the "default when absent" (`enter: { effect: "none", duration: 0.6 }`, `exit: { effect: "none", duration: 0.5 }`), which is semantically indistinguishable from having been explicitly set to this value.
- `duration`/`delay` are always numbers in seconds; when the attribute is absent, the default is filled in (effects with `family === "media"` default to `duration: 0`, all other families default to `duration: 0.6`; `delay` always defaults to `0`).

**Error cases**

| Case | `failureKind` |
|---|---|
| `presentation-id` does not exist | `not-found` |
| `slide-path` does not exist | `not-found` |
| This slide has no `<slidra:effects>` list at all (no effect was ever added) | `not-found` |
| Any item in the list is missing a required attribute (`target`/`family`/`effect`/`start`) | `failed` |
| The value of `family`, `effect`, or `start` is not in its respective fixed set | `failed` |
| `family === "path"` but the `d` attribute is missing | `failed` |
| The `duration`/`delay` attribute is present but is not a legal non-negative number of seconds (including the case where the attribute is present but is an empty string) | `failed` |
| The `target` of some item points to an element that does not exist on this slide | `failed` |
| The first item in the list has a `start` other than `on-click` (there is no preceding step to merge into) | `failed` |
| This slide's `<metadata>` contains more than one `<slidra:effects>` element (the structure is corrupted) | `failed` |

> "This slide has no effect list yet" is `not-found`, and this is shared with the judgment used by the other `effect`-family commands (all except `add`, i.e. `remove`/`move`/`set`): `effect list` reports `not-found` for a slide that has never had any effect added — it does not return an empty `effects: []` list. Only `effect add` creates the list when it does not exist. When the list exists but is empty (in theory: effects were added and then all removed, so the `<slidra:effects>` element remains but has no children), it normally returns `effects: []`, `steps: []` — not an error. When the list's content itself is corrupted (the remaining rows in the table above), it is always classified as `failed`, because that is "the content is invalid" rather than "the list cannot be found".

**Example**

```
slidra effect list pres-abc123 slides/001.svg
```

## `chart data set`

**Syntax**

```
slidra chart data set <presentation-id> <slide-path> <element-id> (--categories <c1,c2,...> --series 'name=v1,v2,...' (repeatable) | --csv <path|-> | --csv-asset <virtual-path>)
```

**Parameters**

- `presentation-id` / `slide-path` / `element-id`: strings, required; `element-id` must refer to a chart element on that slide.
- The data source is **exactly one of**:
  - `--categories <c1,c2,...>` combined with one or more `--series 'name=v1,v2,...'` flags (repeatable, one series per flag); `values` is a comma-separated number list.
  - `--csv <path|->`: `path` is a local filesystem path, or the literal string `-` to read from standard input (see the general rule "`-` means standard input"). The content must be CSV following RFC 4180 quoting rules (series names may contain commas), with or without a BOM (which is stripped), accepting both `\r\n` and `\n`, and ignoring trailing blank lines; the first column is the category names, and the remaining columns are the series names and their values.
  - `--csv-asset <virtual-path>`: the virtual path of a CSV file under `assets/` inside the container; the content goes through the same CSV parsing logic.
  - This "exactly one of three" requirement is a **validated invariant**, not three independently optional flags that merely happen to be given one at a time: when invoked from the command line, giving zero or two-or-more of them fails immediately at the parsing stage (see below); when invoked directly through `slidra serve` with structured input, exactly one must still be given, and violating this returns a failure.
- `--csv -`: the CLI entry layer substitutes `-` with the full text read from stdin before `dispatch`, passing it through the internal field `csvText` (not `csv`). `slidra serve` has no terminal stdin to read from — if the handler receives a `csv` whose literal value is still the un-substituted `"-"`, it must fail immediately, with a message meaning "`--csv -` can only be used from the command line."

**Success `data`**

```json
{}
```

**Error cases**

| Scenario | `failureKind` |
|---|---|
| `presentation-id` does not exist | `not-found` |
| `slide-path` does not exist | `not-found` |
| `slide-path` exists but is not listed in that presentation's `slides`/`templates` list | `failed` |
| `element-id` is not found on that slide, or is found but is not a chart element (missing `data-slidra-type="chart"`) | `failed` |
| Zero or two-or-more of the three data sources are given | `failed` |
| The local file specified by `--csv <path>` does not exist | `not-found` |
| `--csv-asset <virtual-path>` cannot be found inside the container | `not-found` |
| `--csv -` but standard input is empty | `failed` |
| Called directly through `serve`, and the value of `csv` is exactly the un-substituted `"-"` | `failed` |
| The CSV / `--categories` + `--series` content is invalid (mismatched column counts, non-numeric values in a numeric column, an empty category list, any series with no values, or an empty series name) | `failed` |

> **Design decision for this spec**: the "exactly one" validation lives in the handler itself (the shared layer that both `serve` and the CLI go through), rather than being checked only once at argv parsing, so that the two call paths behave consistently.
>
> **When `element-id` does not exist, or is not a chart element, the `failureKind` is `failed`, not `not-found`**. This is consistent with other chart commands (`chart type set`, etc.), the `table` family of commands, and the `element` family of commands, but differs from the intuition elsewhere in this document that "an id that can't be found is `not-found`" — called out specifically here to avoid mistakes.

**Example**

```
slidra chart data set pres-1 slides/001.svg el-1 --categories Q1,Q2,Q3 --series 'Revenue=100,120,140'
cat sales.csv | slidra chart data set pres-1 slides/001.svg el-1 --csv -
```

## `asset import`

**Syntax**

```
slidra asset import <presentation-id> <source> [--as csv]
slidra asset import <presentation-id> --svg <markup> --name <filename.svg>
```

**Parameters**

- `presentation-id`: string, required.
- `source`: string, required. If it begins with `http://` or `https://` it is treated as a URL and always downloaded via `fetch`; otherwise it is treated as a local filesystem path and read via `readFile`. **Relative paths are valid and are resolved relative to the CLI process's current working directory** (this is a settled decision that freezes existing behavior).
- `--as`: string, optional. The only valid value is `csv`, indicating this is a data asset rather than a media asset; any other value fails immediately. When `--as` is omitted, the existing media import path is used (byte-for-byte compatible with existing behavior).
- `--svg`: string, optional. Creates an SVG asset directly from content given on the command line; mutually exclusive with the `source` positional argument and `--as`. The content's root node must be `<svg>`, and `<script>`/`<foreignObject>` are not allowed.
- `--name`: string, can only be given together with `--svg`, and is required in that case. Only `[A-Za-z0-9_-]+\.svg` is allowed; it is written to `assets/<filename>`, with **no conflict-renaming**: if a file with the same name already exists, it fails (background recipes rely on path reuse, and silently renaming would break that reuse). The success `data` is `{ "path": "assets/<filename>", "mimeType": "image/svg+xml", "kind": "image" }`.

**Success `data`**

Regular media import:

```json
{ "path": "assets/photo-1.png", "mimeType": "image/png", "kind": "image" }
```

With `--as csv`:

```json
{ "path": "assets/data/sales.csv", "mimeType": "text/csv", "kind": "data" }
```

`kind` takes values from `image | video | audio | data`. The format is determined **purely from the file's header bytes, not the extension** (ADR-0015). On a filename conflict, `resolveAssetImport`/`resolveDataAssetImport` each generate a non-conflicting filename within their own numbering space (regular media falls under `assets/`, data assets fall under `assets/data/`), and the two do not interfere with each other.

**Error cases**

| Scenario | `failureKind` |
|---|---|
| `presentation-id` does not exist | `not-found` |
| The local source file does not exist or cannot be read | `not-found` |
| The URL download fails (a connection error, such as DNS resolution failure or connection refused) | `failed` |
| The URL response is not a 2xx status code | `failed` |
| The value given to `--as` is not `csv` | `failed` |
| The header bytes don't match any supported media format (and `--as csv` was not given) | `failed` |
| `--svg` is given together with `<source>` or `--as`; `--svg` is missing `--name`; `--name` doesn't match the required format; the `--svg` root node is not `<svg>` or contains a disallowed element; `assets/<filename>` already exists | `failed` |

> **A nonexistent local source file → `not-found`**: this is for consistency with the convention that when `chart data set --csv` reads a local file and gets an ENOENT, it maps to `SlidraNotFoundError` (`not-found`).

**Example**

```
slidra asset import pres-abc123 https://example.com/photo.png
slidra asset import pres-abc123 ./sales.csv --as csv
```
## `slide add`

**Syntax**

```
slidra slide add <presentation-id> [--template <template-path>] [--svg <markup>] [--at <index>]
```

**Parameters**

- `presentation-id`: string, required.
- `--svg`: optional string, a full-page SVG markup (see ADR-0018): the agent writes an entire page at once, and Slidra runs an ingest pass before writing it — the root node must be `<svg>`; if `viewBox` is omitted it is filled in from the canvas size, and a mismatch with the canvas is rejected; every `<text>` element placed directly under the root `<svg>` that carries `data-slidra-text-width` (a "text box declaration") is converted into an actual text box (producing the same `<g>` structure that `textbox add` produces: `x`/`y` is the top-left corner, content is split into paragraphs by line breaks, `data-slidra-list` gives one token per paragraph, `data-slidra-text-align` sets alignment, `font-size` defaults to 24 when omitted, `font-family` defaults to Noto Sans TC when omitted; a declaration must not contain child elements). After that, the same normalization as `convert` runs (bare graphic primitives get wrapped in `<g>`, ids are filled in, transforms are moved onto the container); anything that cannot be fixed — `<script>`/`<foreignObject>`, duplicate ids, etc. — is rejected outright and nothing is written. `<defs>`, `<style>`, gradients, filters, clipPath, and `path` are all allowed. The agent may supply its own `id`s. Mutually exclusive with `--template`.
- `--template`: optional string, the virtual path of a template listed in `project.json`'s `templates` array; if omitted, a blank slide is added (a compliant `<svg>` with no elements, sized to the presentation's current canvas dimensions). When applying a template, its content is copied byte-for-byte, but every element's `id` (and the effect/comment `target` values that reference those ids) is regenerated to avoid colliding with the template itself or with other slides already produced from it.
- `--at`: optional, a numeric string; if omitted the slide is appended after the last one. Must be an integer between `0` (start of the list) and the current total slide count (end of the list, equivalent to appending), inclusive; only "is this a valid number" is checked during parsing — whether it's an integer and within range is validated at execution time.

**Success `data`**

```json
{ "slidePath": "slides/003.svg" }
```

The new slide's virtual path uses the smallest unused `NNN.svg` number currently available under `slides/`, not a simple increment. When `--svg` is given, an additional `elementIds` field is included (all top-level container ids, in document order):

```json
{ "slidePath": "slides/003.svg", "elementIds": ["el-title", "el-a1b2c3d4e5f6"] }
```

**Error cases**

| Situation | `failureKind` |
|---|---|
| `presentation-id` does not exist | `not-found` |
| The path given to `--template` does not exist at all (neither a template nor a slide) | `not-found` |
| The path given to `--template` is actually a slide, not a template | `failed` |
| `--at` is not an integer, or is outside `0` to the current slide count | `failed` |
| `--svg` and `--template` are both given | `failed` |
| `--svg`'s root node is not `<svg>`, its `viewBox` doesn't match the canvas, a text box declaration has child elements or isn't directly under the root `<svg>`, or normalization hits an unfixable issue (`<script>`, duplicate ids, etc.) | `failed` |

**Example**

```
slidra slide add pres-abc123
slidra slide add pres-abc123 --template templates/001.svg --at 0
slidra slide add pres-abc123 --svg '<svg viewBox="0 0 1280 720" style="background-color:#101418"><text id="el-title" data-slidra-text-width="1120" x="80" y="72" font-size="40" font-weight="700" fill="#F4F6F8">Title</text></svg>'
```

- `template-path`: string, required. Must be the `file` value of some entry in `project.json`'s `templates` array. Deletion removes both the SVG file and its entry in the `templates` array, wrapped in the same history group (one undo restores both together). Per ADR-0013, deleting a template **does not** check, scan, or warn about any slides that were previously created from this template — once a template has been applied, it becomes unrelated to the resulting slides.

**Success `data`**

```json
{}
```

Same as `template rename`: the handler returns `{ ok: true, message }`, with no `data` field at all (type `void`); the bin prints no JSON, only the `message`.

**Error cases**

| Situation | `failureKind` |
|---|---|
| `presentation-id` does not exist | `not-found` |
| `template-path` is not in the `templates` array, but happens to be a path in the `slides` array | `failed` (message: "not a template: `<template-path>` (use slide delete to delete a slide)") |
| `template-path` is neither in `templates` nor in `slides` | `not-found` |

**Example**

```
slidra template delete pres-1 templates/001.svg
```
## `comment add`

**Syntax**

```
slidra comment add <presentation-id> <slide-path> <target> <text> [--author <name>]
```

**Parameters**

- `presentation-id`: string, required.
- `slide-path`: string, required, must be a slide in `project.json`'s `slides` array (templates don't apply — both notes and comments are only meaningful for slides); moreover, that slide must be in "compliant" form (already run through `convert`, with every selectable element being a `<g id="…">` container) — the comment feature parses the element list based on this normalized form.
- `target`: positional argument, required, either the literal string `"page"` (a slide-level comment) or the id of an existing element on that slide.
- `text`: positional argument, required. Command parsing allows an empty string (it only checks whether the argument was "fully omitted"), but **the core layer rejects a string that is empty after trimming leading/trailing whitespace**, so comment content effectively cannot be blank.
- `--author`: optional string; defaults to `"agent"` if omitted. Also cannot be empty after trimming.

**Success `data`**

```json
{ "commentId": "c-a1b2c3d4" }
```

**Error cases**

| Situation | `failureKind` |
|---|---|
| `presentation-id` does not exist | `not-found` |
| `slide-path` is not in the presentation's `slides` array | `failed` |
| `--author` is empty after trimming | `failed` |
| `text` is empty after trimming | `failed` |
| The slide is not in compliant form (not yet `convert`ed, or has structural issues) | `failed` |
| `target` is not `"page"`, and no matching element is found on the slide | `failed` |

**Example**

```
slidra comment add pres-abc123 slides/001.svg page 'The overall color scheme could be darker'
slidra comment add pres-abc123 slides/001.svg el-title 'Title font is too small' --author reviewer1
```

**Syntax**

```

**Parameters**

- `presentation-id`: string, required.
- `slide-path`: positional argument, optional. ## `deck list`

**Syntax**

```
slidra deck list <path> [--owner <owner>]
```

**Parameters**

- `path`: string, required. A local filesystem path — either a directory to scan (non-recursive) for `.slidra` files (matched by extension, case-insensitive), or a single `.slidra` file to describe on its own. Unlike every other command, this is a real filesystem path, not a `<presentation-id>` — the folder being scanned may hold decks that have never been `open`ed and therefore have no id yet.
- `--owner`: string, optional. When given, only decks whose `owner` (see `project.json`'s `owner` field, [`workspace.md`](workspace.md)) exactly equals this value are included; decks with no `owner` at all never match, even against `--owner ''`.

**Success `data`**

```json
{
  "decks": [
    { "fileName": "Q3.slidra", "name": "Q3 Report", "slideCount": 4, "owner": "alice" },
    { "fileName": "broken.slidra", "name": null, "slideCount": null, "owner": null }
  ]
}
```

Each entry's `fileName` is the file's basename only — never a full or absolute path (ADR-0004). A file that fails to open or parse (a not-yet-migrated legacy ZIP, a corrupted container) contributes one entry with `name`/`slideCount`/`owner` all `null`, rather than failing the whole command — a single bad file must never hide every other deck in the folder.

**Error cases**

| Condition | `failureKind` |
|---|---|
| `path` does not exist | `not-found` |

**Example**

```
slidra deck list ~/Slidra --owner alice
```

## `deck meta set`

**Syntax**

```
slidra deck meta set <path> [--name <name>] [--owner <owner>]
```

**Parameters**

- `path`: string, required. The local filesystem path of an existing `.slidra` file — like `deck list`, this operates directly on a path rather than a `<presentation-id>`, since it is also used before a deck is ever registered.
- `--name`: string, optional. Overwrites `project.json`'s `name` field.
- `--owner`: string, optional. Overwrites `project.json`'s `owner` field. An explicit empty string is a legal value, written as-is.

At least one of `--name`/`--owner` must be given. Every other field already in `project.json` (including an `owner` this command isn't touching) is left byte-for-byte untouched, in its original position.

**Success `data`**

```json
{}
```

**Error cases**

| Condition | `failureKind` |
|---|---|
| Neither `--name` nor `--owner` is given | `failed` |
| `path` does not exist, or is not a valid `.slidra` container | `failed` |

**Example**

```
slidra deck meta set ~/Slidra/Q3.slidra --owner alice
```

## Internal commands

Two more commands are dispatched by Rust (`commands::CORE_TAKEOVER`, alongside `undo`/`redo`) but are deliberately NOT among the command-entry-format commands above, and are NOT listed in `packages/server/agent-workdir/reference/commands.md`: they exist solely for `packages/server`'s own turn grouping (`agent/session.ts`) to call, never for an agent to invoke directly. Their headings below intentionally do not use the `` ## `name` `` form — that form is reserved for the spec-normative, agent-facing commands counted above, and using it here would make `scripts/check-reference-subset.mjs` and `crates/slidra/tests/cli_golden.rs`'s `cli_md_lists_exactly_the_89_rust_dispatched_commands` require them to also appear in `reference/commands.md`, defeating the point.

### `history begin-group`

`slidra history begin-group <presentation-id>` — opens a group that spans multiple subsequent commands so they undo together as one step. `data: { "opened": boolean }` — `true` when this call is the one that opened the group (the caller owns it and must call `history end-group`); `false` when a group was already open (the caller joined it and must not close it).

### `history end-group`

`slidra history end-group <presentation-id>` — closes the group opened by `history begin-group` and pushes it onto the undo stack as one step (an empty group is discarded, not pushed). `failureKind: "failed"` when no group is open.
