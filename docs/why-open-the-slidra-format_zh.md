# 為什麼我們開放 `.slidra` 格式

[Multilingual: [English](./why-open-the-slidra-format.md)]

**一個建立在開放標準上的投影片格式：座標寫得清清楚楚，模型算得出來，任何人都能播放。**

## TL;DR

- Slidra 是一套讓 AI 協作做簡報的產品，靠四道邊界撐起來：**表示**（`.slidra` 格式）、**動作**（CLI）、**行為**（Skills 與操作準則）、**驗證**。這個 repository 開放的是第一道「表示」，外加一個能播放它的參考 viewer。
- 最值得共享的就是這一道。指令、準則、驗證器都是「處理 deck 的方法」，格式則是 deck 本身。格式公開之後，誰都能圍繞它打造自己的生成器、編輯器、驗證器或播放器。
- `.slidra` 建立在 **SVG** 上。SVG 是 W3C 標準，每個瀏覽器本來就會畫。每張投影片都是一份完整、看得懂的 SVG，不是某家私有的中間格式。
- SVG 裡每個物件都放在**固定畫布上的明確座標**。對 AI 來說，排版因此變成算得出、也驗得了的算術，不再是某個看不見的排版引擎算出來的結果。
- 格式只在 SVG 之上補簡報真正需要的東西：投影片順序、穩定的物件 ID、宣告式的動畫與轉場、講者備忘稿、內嵌字型與媒體，全部裝在一個自給自足的檔案裡。
- 參考 viewer 定義了 deck 該怎麼「播」，也示範了怎麼安全地顯示 AI 生成、不可信任的投影片內容。

---

## 缺的是一個共同的目標格式

AI 生成投影片早就不只是 demo。模型能研究主題、安排敘事、產出整份簡報。但仔細看這些系統輸出了什麼，會發現各做各的：自帶換頁腳本的 HTML、各種 Markdown 方言、一張張投影片截圖，或是透過函式庫寫出、大部分格式細節都被藏起來的 PowerPoint 檔。

每個選擇單獨看都合理。放在一起，結果就是生成的簡報幾乎都綁死在產生它的工具上：換工具會掉東西，事後想改常常改不了，模型寫出來的東西不實際渲染也沒辦法檢查。

**生態系缺的不是再多一個生成器，而是一個共同的目標格式：讓機器寫得好、人拿得出來講、任何工具都讀得懂。**

這就是我們把 Slidra 的這一部分開放出來的原因。

## 第一部分：為什麼是 SVG

### 用開放標準，不另起爐灶

SVG 是 W3C 標準，所有瀏覽器都已支援十多年，設計工具、文件處理流程和各主流語言的繪圖函式庫也都認得它。`.slidra` 的每張投影片都是合法的 SVG，丟進瀏覽器就看得到。

也就是說，這個格式站在一套成熟、到處都有實作的渲染模型上，而不是自己發明一套。想讀 deck 的人，畫投影片這件事不需要任何 Slidra 的程式碼。最難的部分，也就是把向量圖形、文字、漸層、圖片、裁切正確畫出來，每個瀏覽器早就做好了。

### 存下來的，就是畫出來的

很多簡報格式存的是一份「中間描述」，之後再由某個渲染器變成畫面。存的內容和畫出來的結果可能對不上，而兩者之間的規則藏在渲染器裡。

`.slidra` 裡，SVG 本身就是畫好的投影片，上面沒有第二層排版。模型寫的、人檢查的、觀眾看到的，是同一份文件。

### 模型本來就會寫

SVG 是純文字，而且在公開網路上大量存在：圖示、圖解、圖表、插畫都是。語言模型看過非常多。請模型產出 SVG 投影片，是讓它使用已經熟悉的語彙，而不是從 prompt 臨時學一套自訂 schema。

## 第二部分：座標為什麼對 AI 重要

### 位置是寫明的，不是排出來的

在 HTML 和 CSS 裡，元素最後落在哪，取決於流式排版、字型度量、視窗大小、繼承的樣式，以及其他元素的順序。位置是「排出來的」，要知道就得真的跑一次排版引擎。模型寫 HTML 投影片，等於在對一個看不到輸出的系統下指令。

SVG 的位置則是「寫明的」。每張投影片都有固定的畫布 `viewBox="0 0 1280 720"`，每個元素都有明確的座標：

```xml
<g id="el-Ab3xK9mQ2pLw" data-slidra-name="Title" transform="translate(96 160)">
  <text x="0" y="0" font-size="64" fill="#f4f6f8">Quarterly Review</text>
</g>
<g id="el-Qm7Rt2Lp9xZa" data-slidra-name="Chart" transform="translate(96 240)">
  <rect x="0" y="0" width="520" height="360" rx="12" fill="#1a1d23"/>
</g>
```

標題在 (96, 160)，圖表佔 x 96–616、y 240–600。沒有其他東西會把它們挪走。

### 排版變成算術

位置是數字，排版決定就變成模型擅長、而且能把過程寫出來的計算：

- **對齊**：兩個元素的 x 相同，就是靠左對齊。
- **間距**：標題基線到圖表的距離是 240 − 160 = 80。
- **不出界**：x + width ≤ 1280 且 y + height ≤ 720，就在畫布內。
- **重疊**：兩個框在兩個軸上的區間都有交集，就是撞在一起。
- **網格**：左右留白 96 px、欄距 32 px 的四欄版面是一條公式，不用反覆試。

模型可以先規劃版面、寫出來，再只看文件本身檢查結果。程式也做得到。出界、重疊、對齊、間距這些檢查，直接從檔案就能算，不需要截圖，也不需要有人盯著看。

### 文字事先排好

SVG 沒有自動換行，這個格式刻意利用這一點。文字框會記下換行寬度，每一行都存成明確的 `<tspan>`。換行在寫投影片的當下就決定好，不會到了另一台電腦又排成別的樣子。再加上字型內嵌在檔案裡，同一份 deck 在每個合規的播放器上都會斷在同樣的地方。

代價我們直說：寫文字框的一方得自己量字寬才能換行。對生成器來說，這是一次性、有解的問題。比起排版在作者的螢幕和觀眾的螢幕之間悄悄走樣，這個代價划算得多。

### 物件有穩定的身分

每個可定址的物件都是一個 `<g>` 容器，帶著不透明、穩定的 ID（`el-` 加 12 個字元）和給人看的名稱。位置與旋轉只寫在容器的 transform 上，不會散落在各個圖形裡。

模型或任何工具因此能精準指出「第 3 張的那個圖表」，而且這個指稱在重新排序、改名、後續編輯之後都還有效。Agent 可以只改一個物件，不必把整張投影片重新生成。動畫也是透過同一組 ID 指向物件。

## 第三部分：`.slidra` 在 SVG 之上補了什麼

SVG 描述的是一張圖，簡報還需要多一點東西。這個格式只補這些，而且不破壞 SVG：

| 需求 | `.slidra` 的寫法 |
|---|---|
| 投影片順序與畫布 | `project.json`：`name`、`canvas`、依序排列的 `slides` |
| 可定址的物件 | 帶 `data-slidra-name` 的 `<g id="el-…">` 容器 |
| 動畫 | 投影片 `<metadata>` 裡一串有順序的宣告式效果：五類共 20 種，時序用 `on-click`／`with-previous`／`after-previous` 安排 |
| 換頁轉場 | 每張各自設定：`fade`、`slide`、`zoom`，含時間長度 |
| 講者備忘稿、註解 | `<metadata>` 裡的 `<slidra:notes>`、`<slidra:comments>` |
| 圖表與表格 | 資料和畫好的 SVG 放在同一個容器 |
| 媒體 | 影片、音訊、YouTube 嵌入，疊在 SVG 佔位框上 |
| 動態文字 | `{{ slide_number }}`、`{{ slide_total }}`、`{{ presentation_name }}` |
| 字型與素材 | 內嵌在檔案裡，附授權資訊 |

有兩個設計特別值得一提。

**動畫是資料，不是程式碼。** 一個動畫就是一行 `<slidra:effect target="el-title" family="enter" effect="fade" start="on-click"/>`。模型不必寫 JavaScript 才能讓東西在點擊時出現，只要宣告意圖，每個合規的播放器都會播出一樣的結果。播放規格把每種效果怎麼動、效果之間怎麼接，都寫到關鍵影格的程度。

**每張投影片自給自足。** 一張投影片的一切，包括圖形、ID、效果、轉場、備忘稿和註解，都在它自己的 SVG 裡。調換順序只動一個陣列，其他什麼都不碰。單張投影片可以獨立生成、替換或檢查，很適合一次處理一張的模型。

整份 deck 是一個 SQLite 檔，裡面只有一張 `content` 表，每個路徑一列。沒有藏起來的工作副本，也不需要打包；讀取端要拿某一張投影片，不必先解開全部。它依然簡單到不需要資料庫引擎也讀得了：這個 repository 的 viewer 用大約 250 行、零相依的 JavaScript 就能解析。

## 第四部分：為什麼要附參考 viewer

格式要有程式讀它才算數。附上 viewer，是為了讓 `.slidra` 第一天就能用，也讓「這份 deck 到底怎麼播」有一個具體、可以檢查的答案。

- **格式描述的都播得出來。** 效果、轉場、媒體、嵌入、字型、圖表、表格、動態文字、講者備忘稿，任何現代瀏覽器都能播。不用 build、沒有相依套件，檔案也不會上傳。
- **它是播放行為的參考實作。** 播放規格和 viewer 的 runtime 描述的是同一套行為：投影片打開時哪些元素先藏起來、一個步驟怎麼排時序、倒退時怎麼重播、轉場怎麼跑。
- **它示範怎麼渲染不可信任的投影片。** AI 生成的、陌生人傳來的 deck 都是不可信任的輸入，而合法的 SVG 可以夾帶 script。viewer 把每張投影片放進沙箱化、opaque origin 的 frame，Content-Security-Policy 只放行它自己的 runtime。投影片裡的 script、事件處理器和 `javascript:` 連結一律不會執行。基於這個格式開發的人可以直接沿用這套模型，不必自己再踩一次坑。

## 對社群的意義

- **做生成器的人**可以直接輸出 `.slidra`，不用再發明一種新的投影片格式。產出的簡報能被任何讀得懂這個格式的工具播放、檢查和編輯。
- **做工具的人**可以寫轉換器、linter、驗證器、無障礙檢查、搜尋索引或播放器，不必取得授權，也不必逆向工程。
- **做研究的人**拿到一種能直接從文件評分幾何品質的投影片表示法。出界、重疊、對齊、閱讀順序都成了算得出來的屬性，拿來做 benchmark 或訓練回饋都很實用。
- **上台簡報的人和組織**拿到的簡報不會跟著工具一起消失：一個開放的檔案，用瀏覽器加上一小段 parser 就讀得到。

## 開放什麼、不開放什麼

| 開放（本 repository） | 不包含（Slidra Pro） |
|---|---|
| `.slidra` 格式規格 | 視覺化編輯器 |
| 播放規格 | `slidra` CLI 與它的指令集 |
| 容器 RFC | Agent 整合、Skills 與 Harness |
| 參考 viewer 與範例 deck | 驗證器與驗證規則 |

這條線是刻意畫的。格式是工具、模型和人應該共享的共同基礎；編輯器、CLI、準則和驗證，是在這片基礎上工作的其中一種方法，也就是我們在上面打造的產品。它們產出的 deck，在開放的 viewer 裡原樣就能播放。

---

## 結語

AI 已經會畫投影片了，它缺的是一個安放投影片的地方：底層是開放標準，每個座標都寫得夠精確、讓模型推得動，也完整到足以承載一份真正的簡報，從初稿一路走到上台。

**我們開放 `.slidra`，是希望 AI 做出來的投影片，任何人都讀得懂、檢查得了、播得出來、留得下來，而不只屬於產生它的那個工具。**
