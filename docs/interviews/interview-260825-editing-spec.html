Editing Feature Spec Design

User interview record · 2026-08-25 · Slidra (an SVG-first presentation editor) · source: session transcript

Decisions made in this session

  • Scope: one large spec covering the "object / geometry / style / organization" core — insert/delete, move/resize/rotate, styling, stacking order, groups, alignment, clipboard, slide add/delete/duplicate/reorder, undo, templates. Tables and charts get their own future spec; the whole deck has exactly one transition effect, stored in project.json.
  • Geometry model: every element is wrapped in a <g transform> "frame" — move, rotate, and group all resolve to one mechanism, and any software opens the file correctly as-is.
  • Text boxes: Slidra computes its own line breaks and writes them as multi-line <tspan>s into the SVG.
  • Resize semantics: Keynote's approach — dragging an edge changes the box width and rewraps text; dragging a corner scales the whole thing proportionally, font size included; groups always scale proportionally.
  • SVG conformance: strict format, throws on non-conforming input; a separate user-triggered normalize command handles conversion.
  • Undo model: a single timeline, one entry per human action, one entry per agent turn; implemented with snapshots, cleared when the file closes.
  • Concurrency freeze: editing is frozen while the agent is acting, from its first command until the end of its turn; thinking time doesn't block editing.
  • Templates and locking: a template is a static SVG; applying it means copying the whole thing. Elements carry a lock flag: fully blocked in the UI, rejected by the CLI but overridable with --force. No master-slide sync, no template swapping — left to the agent to handle by editing pages directly.
  • Dynamic text: {{ slide_number }} is written directly into the text content and substituted at render time; only variable substitution, no logic, starting with three variables.
  • Asset import: the agent can import via an absolute path or a URL, always landing in assets/, with the actual media format validated on import.
  • Command granularity: one command can act on multiple elements; one operation is one undo entry.
  • Style commands: a general-purpose element style set command, with attribute names matching SVG attribute names directly, gated by an allowlist — the allowlist protects geometric invariants, not security.
  • Element kinds: a fixed list plus arbitrary paths (paths can only be manipulated as a whole, no node editing).
  • Duplication and effects: effects travel with the element, appended to the end of the target's effect list.
  • Clipboard scope: limited to within the same deck, plus support for pasting images from the system clipboard.
  • Template swapping: not provided; the agent helps migrate content instead.
  • Deferred to future tickets: bundling fonts into .slidra, tables, charts, cross-deck content transfer.

(Worth noting the rhythm of this conversation up front: the user repeatedly interrupted AskUserQuestion prompts, asking to "explain it to me like I'm 15" and "walk me through the pros and cons of each option in plain language" — each time forcing a plainer explanation. The biggest feature of the whole session is how often the answer chosen was completely overturned in the very next turn. Each of these is flagged below as it happens.)

Geometry model: how should an element's position be written (question 5)

AI

Current state: every kind of thing in SVG speaks its own dialect — text has an anchor point, rectangles have a top-left corner plus width/height, with no unified way to talk about position, and nowhere to write "I'm rotated 15 degrees." Moving, resizing, rotating, and grouping all require inventing this unified vocabulary first — it's the foundation the whole spec rests on.

AI (asking)

How should an element's position and rotation be written into the SVG?

  • Wrap each element in a container (recommended) — always a <g>, with position and rotation written into its transform, while size stays element-specific. One mechanism resolves all three concerns. Cost: one extra element per object, and absolute coordinates need computing.
  • Record an explicit box on each element — clearest for resizing, but storing the same fact in two places will drift out of sync silently, and rotation would be a made-up attribute, violating ADR-0001.
  • No container, edit the native attributes directly — the cleanest SVG, but rotation has no solution, and moving a group means touching every child element.
User

Walk me through the pros and cons of each option in plain language.

AI

Using a "picture frame" analogy: option one puts the object inside an invisible frame — moving it means moving the frame, rotating it means rotating the frame, and a group is a frame containing more frames — moving a group by one centimeter only touches the outermost frame. Option two has each object keep its own box, which is clearest for resizing and alignment, but the box and the x/y coordinates become two competing sources of truth, and the rotation attribute is invented, so other software opens the file and sees no rotation at all. Option three keeps bare attributes — the cleanest SVG, but rotation has no solution and moving a group means touching every child element. Verdict: option one, because it's the only one where a single mechanism solves moving, rotating, and grouping together — the other two will eventually have to grow a <g transform> halfway through anyway to patch the gap.

User

If I want the original SVG to look correct when opened as-is, is there a good option for that?

AI

This requirement picks the answer directly — and it picks option one. <g> and transform are core SVG syntax, not something Slidra invented, so any software opens it correctly, rotation included. Option two breaks: other software ignores the made-up attribute, so a title rotated 15 degrees opens looking upright. The one thing still worth watching is fonts — that's a separate question.

AI (asking)

Geometry model, final call: how should an element's position and rotation be written into the SVG?

  • Option 1: wrap in a frame (recommended) — fully native SVG, opens correctly in any software.
  • Option 2: explicit box — rotation is a made-up attribute, directly violating the requirement just raised.
  • Option 3: no wrapping, edit native attributes directly — trades away rotation to get a correct as-is view.
User (answer)

Going with option 1. Open a separate ticket for bundling fonts into .slidra.

Text boxes (question 6)

AI

SVG's <text> doesn't wrap automatically — that's a spec limitation, not a lazy implementation. PowerPoint/Keynote text boxes auto-wrap, which is a basic user expectation. Three routes: A, implement text boxes ourselves (Slidra computes line breaks and writes multiple tspans; other software still opens it correctly; the cost is recomputing line breaks on every text edit, a risk already mitigated by the font-bundling ticket); B, one element per line (honest, but typing a paragraph would be painful); C, <foreignObject> (already blocked by ADR-0005, not worth considering).

AI (asking)

Should text have a "text box" (with a width, auto-wrapping)?

  • A: implement text boxes ourselves (recommended) — user experience matches PPT, and other software still opens the file correctly.
  • B: one element per line — typing a paragraph is extremely painful, and changing font size means editing a pile of elements.
User (answer)

A: implement text boxes ourselves (recommended)

Resize semantics: PowerPoint or Keynote (question 7)

Dragging an edge only changes box width and rewraps text; dragging a corner scales the whole thing proportionally, font size included; groups always scale proportionally. Cost: font sizes can end up with decimals.

SVG conformance (question 8)

AI

Option one is a format convention, but SVG doesn't force anyone to follow it. Three sources of non-conformance: the existing demo (bare elements), the user hand-editing files, and SVGs coming in from Figma or elsewhere. Layouts and masters: from "master slide" all the way to "template + lock"

AI

"Change the master, everything changes together" inherently violates ADR-0003 + ADR-0008 (a slide is self-contained). First round, three proposals: A, a layout is a starting template (copied once, then independent; the ADRs stay untouched, and "change once, apply everywhere" is left to the agent); B, a true master slide (composited at display time, but a single opened page would be missing its background, overturning ADR-0001); C, the master is real but baked into every page on edit (feels like PPT, at the cost of tracking per-attribute "was this given by the master or edited by the user," which is the easiest part of this whole spec to get wrong). AI recommends A: Slidra has an agent, so "change the whole deck's background color" is one sentence to it — no need to buy, through a complex inheritance mechanism, something the agent already gives for free.

Concurrency and freezing (question 14)

AI

Current state: live-reload.ts's events carry no content — the frontend just fully reloads on receipt. That's fine when only the agent is making changes, but once editing ships, it will break: the user is dragging a box, the agent finishes editing a different element, the screen fully reloads, and the box in the user's hand snaps back to its original position. Three approaches: one, buffer during dragging, apply once released (low cost, but doesn't guarantee correctness, only lowers the odds of a problem); two, commands carry expected state as an optimistic lock (the only genuinely correct option, but if the user moves something while the agent is still thinking, the command fails and has to reread and recompute); three, don't handle it at all (this scenario is common, but the actual odds of harm are fairly low). AI recommends approach one.

AI (asking)

  • Commands carry expected state (optimistic lock)
  • Don't handle it

The page must temporarily freeze while the agent is making changes.

AI

What freezes is editing, not browsing — the user can still scroll, switch pages, and enter play mode; they just can't drag or edit. What needs pinning down is "how long is frozen." Three approaches: one, freeze for the agent's entire turn (simplest state, but if the agent thinks for thirty seconds, editing is blocked for those thirty seconds even though no conflict could actually occur then); two, freeze only for the instant each command executes (shortest freeze duration, but a turn might flash a dozen brief freezes, and a drag spanning one of those moments still gets interrupted); three, freeze from the first command until the end of the turn (editing is allowed while the agent is still thinking/reading, locks the moment it starts acting, and stays locked until the turn ends — sharing the same boundary as "one undo entry per agent turn"). AI recommends approach three.

AI

Everything worth asking has been asked; the rest follows directly from existing ADRs without further discussion: speaker notes live in that page's SVG <metadata>, the same place as the effect list; snapping and guide lines are frontend assistance and don't add new commands, while alignment is a command (inherently multi-element); stacking order is four semantic operations; extensions to selection (multi-select, marquee-select, entering a group to edit) are frontend behavior and produce no commands; a group is itself an element, with an id and a display name, and can be nested; templates live in .slidra's templates/*.svg; slide-level operations (add, delete, duplicate, reorder) are each one command.
