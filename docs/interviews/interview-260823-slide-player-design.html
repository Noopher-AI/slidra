Slide Player Design

User interview record · 2026-08-23 · CoMotion (an SVG-first presentation editor) · source: session transcript

Decisions made in this session

  • ADR-0007: playing a .comot file requires CoMotion to be installed; sharing happens through export (Export HTML / PDF / PPTX), not by handing over the file. This supersedes ADR-0005's rule that "the runtime must not depend on a server."
  • Step scope is per-page, not continuous across the whole deck; the total step count is computed, never stored.
  • A slide's static appearance is the end state with every effect already played out. Hiding elements is something the runtime does only during playback, and is never written to the file; elements with no effect are visible from the very start.
  • ADR-0009: animation is an ordered list of effects inside the slide SVG's <metadata>, expressed with a custom XML namespace — modeled on PowerPoint's <p:timing> tree and Keynote's build list, rather than as attributes on the element. Steps are derived from the list, not stored separately.
  • ADR-0008: a single slide is self-contained; swapping two pages requires touching no third file.
  • Audio must be attached to a visible element (that's its selection handle), preserving the invariant that "every effect points at an element."
  • ADR-0010: slide content is untrusted. View mode never runs scripts; only play mode adds allow-scripts, and never allow-same-origin. The runtime must capture keyboard input itself, since transient activation doesn't survive a postMessage hop.
  • The sidebar overview shows real thumbnails using zero-token sandboxed iframes, lazily loaded.
  • This round covers playback only: no write commands, no agent involvement; the test deck was deliberately handwritten, as an honest check of whether the format is human-friendly.

A pivot: from step-driven animation to a player

User

I've decided — the next big direction is to build a feature in CoMotion, a mode that behaves like a slide-deck player. Skip all the editor basics for now: you should be able to see a sidebar overview of the deck, click into it to see each slide, hit play to go fullscreen, and press the arrow key to advance to the next slide. That's the shape I want.

As for editing, let's not build that yet — playback is enough for now. Playback should include video, audio, and image playback. I also want some animation here, the simplest case being: I press next, the first object appears; I press next again, the second object appears. Or, once I move to the next page, a video that was static starts playing when I advance. Or an audio file on the slide starts playing once I press next.

So the goal is an interface that can present a deck. All of this content should come from my custom .comot file format — it needs to live inside that, and be played back from it.

I don't want you to just dive in and start building. I think you should look online first to see if there's existing prior art you can draw on, and pull it in for reference if it's useful.

ADR-0007: playback requires CoMotion

AI

This is a major pivot — let's tally the trade-offs clearly.

Gained: the runtime can now depend on a server, so video/audio can stream through /api/raw with HTTP Range support (this is where that capability first becomes meaningful); the player and the editor share the same web app; a future Mac app just hides the server, with no architectural change needed.

Lost: the door to export --html closes; sending a .comot file to someone without CoMotion installed produces a dead file, which is in tension with ADR-0003's premise that "a deck can be copied, sent, and backed up." Presenting on a given machine now requires CoMotion installed there. The one remaining escape hatch — that opening a single slide SVG directly in a browser must still show a correct static image — is therefore promoted to a final compatibility guarantee that can no longer be eroded.

This framing was later overturned entirely by the user. In the next message the user pointed out that "sharing" isn't actually lost, because CoMotion could later implement Export HTML / Export PDF / Export PPTX, still allowing conversion to other formats to share with others — only the .comot file itself is CoMotion-exclusive. The ADR was ultimately written around this framing: not "can't be shared," but "shared via export, not via handing over the file."

Question 2: how to record this — write a new ADR-0007 that supersedes that part of ADR-0005, or edit ADR-0005's text directly? The AI recommended the former, reasoning that an ADR is a decision record, not a spec — erasing the context of a past decision means future readers (human or agent) lose sight of what tradeoffs were actually weighed.

User

Agreed, go ahead and make that change. One more thing to add — nothing is actually lost, because in the future I can implement Export HTML, Export PDF, even Export PPTX inside the CoMotion app or server. All of that is achievable. So none of that capability is lost; it can still be converted to other file formats to share with others — it's specifically the .comot extension that only runs inside CoMotion.

AI

This addition rewrites the cost column: it's not "can't be shared," it's "shared via export, not via handing over the file" — .comot is a working format, not a delivery format.

One tension flagged but deferred: ADR-0001 states plainly that "CoMotion neither imports nor exports PPTX," which conflicts with just having listed PPTX as a future export option. The call is to leave ADR-0001 untouched for now, and open a new ADR against it when PPTX export actually gets built.

ADR-0007 was written, ADR-0005 got a superseded-by note (with its original reasoning left in place), and the README was updated in two spots. Question 1 is answered by this decision: the player isn't a standalone artifact, it's a mode of the same web app.

Step scope (question 3)

AI (asking)

Is a "step" scoped to a single page, or continuous across the whole deck?

  • A. Per-page scope (recommended) — each page's steps recount from 1.
  • B. Global continuity — step numbers run continuously across the whole deck.

Recommending A: ADR-0001 says an SVG has no more authoritative representation, so global numbering would make a step number meaningless when a single slide is opened on its own; ADR-0003 already made the same call for an equivalent problem (using an explicit slides array instead of filename ordering), to avoid mass renumbering when reordering. The cost: the "total step count" doesn't live in any single file — it has to be computed by the runtime — which is correct, since storing it would just be a cache, and caches drift out of sync.

Where hidden state lives (question 4)

AI (asking)

Does the "not yet appeared" hidden state of an element live in the file, or only in the runtime?

  • A — stored in the file, with the element carrying display="none" or opacity="0".
  • B (recommended) — only lives in the runtime: every element in the file is in its visible, final state, and the runtime hides then progressively reveals them at playback time.

Recommending B, and arguing A is outright invalid: under A, opening an animated slide in Illustrator would show a nearly blank page — exactly the picture ADR-0001's static-compatibility acceptance criterion forbids, and after ADR-0007 this guarantee is the only way left for someone without CoMotion installed to see any content at all. Under B, the static appearance equals the end state after all steps have played, so edit mode gets the correct picture for free, and data-comot-step degrades to a pure marker with no effect on rendering. Also settled in passing: an element with no annotation belongs to step 0, and is already on screen when the page loads. The cost is that the implementation has to hide-then-reveal, which can cause a momentary FOUC — a known, solvable problem.

User (answer)

B

Defining "enter" — the first version asked at the wrong altitude (question 5)

AI (asking)

Is media "playback" the same thing as an element's "entrance," or are they two separate things?

  • A (recommended) — unify them: a single mechanism that means "appear" for static graphics and "start playing" for media assets, with the runtime dispatching by element type.
  • B — split into two: one set of attributes for appearance, another for media triggers.

Recommending A, at the cost of revising CONTEXT.md's definition of "enter" — loosening it from "how something appears" to "what an element does when triggered: appearing for static elements, starting playback for media assets."

This was later judged to have asked the question at the wrong altitude, and the loosened definition was withdrawn. The user didn't choose between A and B, but instead asked for research into PowerPoint's and Keynote's data models first, for future extensibility. The AI subsequently admitted this question was "asked at the wrong altitude" — the real question wasn't "should entrance cover media," but "should animation data live on the element's attributes, or in an ordered list." The definition of "enter" therefore didn't need loosening after all — it reverts to covering only the appearance of static elements, with media playback becoming its own separate effect family. See question 5 (revisited) below.
User

I want to discuss this with you, because there will be more animation transitions down the line, not just "appear" — there will be more presentation-playback states in the future too. So I want you to think more carefully about how presentation software like PowerPoint and Keynote is designed, so this holds up better for future extensibility.

AI

Looked into PowerPoint's and Keynote's actual data models. PowerPoint's animation lives in <p:timing>, a tree completely separate from the shape tree, pointing back at shapes via <p:spTgt spid="3">; effects are grouped into families (entrance, emphasis, exit, motion path), and media play/pause/stop are just effect entries in the same list rather than a separate mechanism — each entry also carries a start mode (On Click / With Previous / After Previous). Keynote is isomorphic: Build In / Build Out / Action. The key finding: "one click" and "one animation" are not one-to-one — `With Previous` exists precisely so multiple animations can share a single click. In other words, a "step" shouldn't be stored at all — it should be derived from an ordered effect list.

Question 5 (revisited): does animation data live on the element itself, or in an ordered list on the slide?

  • A — lives on the element (ADR-0005's current wording).
  • B (recommended) — an ordered list inside <metadata>, with each entry pointing at an element id.

Recommending B: A has a structural ceiling — an element can only carry one effect, which can't express "enters at step 2, is emphasized at step 5, exits at step 7." The ordering argument is the same one that won question 3 — a list turns inserting an effect into a splice, whereas attributes would mean renumbering every step after it. <metadata> is valid SVG and other tools ignore it, so it doesn't conflict with ADR-0001. The cost: orphaned effect entries (deleting an element requires cleaning up effects that point at it), and animation and elements now live in two places (though under ADR-0002 the CLI wraps this away). Scope for this round: the structure fully supports all four families and all three start modes, but only "on click" as a start mode and "entrance" plus "media playback" as effect families are actually implemented.

Runtime environment, fullscreen, and focus (question 6)

AI (asking)

First checked two technical facts that would decide the answer: transient activation does not survive a postMessage hop (if the parent document listens for the arrow key and posts a message to the iframe to play audio, it will fail), so key presses must be captured by the runtime itself; and a parent document can call requestFullscreen() on its own iframe element without needing to grant the iframe fullscreen permission.

Should the runtime run inside a sandboxed iframe, or should the iframe be abandoned?

  • A (recommended) — keep the iframe, add allow-scripts during playback (never allow-same-origin), with the runtime listening for the keyboard itself.
  • B — abandon the iframe, inline the SVG directly into the parent document, and rely on server-side sanitization to block untrusted content instead.

Recommending A: view mode stays zero-script, and only play mode enables scripts; also, since playback is always fullscreen, nothing on screen would compete with the iframe for focus, so the classic "pressing space does nothing" bug can't happen under this design.

This reasoning was later overturned by the user's next message. The user insisted fullscreen must be something the user explicitly chooses, not hardcoded into the app — which invalidates the argument that "playback is always fullscreen, so focus can never be stolen." The AI acknowledged the focus problem was back, and in the same response rejected a proposed fix — having the parent document also listen for the arrow key as a fallback — because that would work for pure visual steps but fail for media steps (since transient activation can't survive the postMessage hop), leaving some steps that respond to a key press and others that don't, which is worse than an outright failure. The final resolution: view and play remain the two modes, and fullscreen becomes a toggle within play mode that can be switched anytime, not a separate mode; when focus isn't on the player, the screen must say so explicitly and offer a way to click back in — it must never silently fail.
User

I want to go with option A, but fullscreen during video playback should be something the user can choose for themselves. It could play inline right where it is without fullscreen, or it could play fullscreen — that choice should belong to the user, not be a default baked into the code.

Sidebar overview: real thumbnails (question 7)

AI

First, a fact that looked tempting during research but turns out unusable: when an SVG is loaded via <img src="...">, the browser forces it into a static, safe mode — no scripts run (which is what we want), but no external resources load either (which is fatal here).

This option was ruled out within the same passage it was raised in. A slide containing a photo or a video poster would show a gap in its <img> thumbnail — and in a presentation tool, a thumbnail missing its image is the same as having no thumbnail at all — so this seemingly zero-cost, safe route was ruled out.

Should the sidebar overview show real thumbnails, or just a list of page numbers?

  • A (recommended) — one zero-token sandboxed iframe per page, the same posture as the current canvas.ts, scaled down; assets load normally, and the trust boundary is unchanged.
  • B — a list of page numbers and names, cheap but gives no visual sense of which page is which.

Recommending A: the thumbnail is the entire reason the overview exists. The cost is one iframe per page, addressed with the lazy loading pattern reveal.js already provides (only instantiating the pages near the viewport).

File format for the effect list (question 8)

AI

The location isn't really a choice: ADR-0003 says project.json only holds what SVG can't express, and the same reasoning applies here — putting the effect list in project.json would mean opening a single slide loses its animation, so it belongs inside that slide SVG's own <metadata>. The real choice is format:

  • A (recommended) — XML elements in a custom namespace, e.g. <comot:effect target="el-a3f2c1" family="enter" effect="fade" start="on-click"/>.
  • B — JSON packed into a text node inside <metadata>.

Recommending A, citing ADR-0004 (hand-readable, agent-friendly): it keeps the whole file in a single syntax.

This argument was retracted within the same passage. The AI initially wanted to cite "XML diffs cleanly line by line in git" as a reason, then immediately withdrew it in the same message: a .comot file is a zip, and the working directory lives in ~/.comotion/work/ — none of it goes into git, so that argument doesn't hold. The real cost was stated plainly instead: XML attribute values are all strings, so adding duration or delay later means writing your own type coercion, which JSON gets for free — and a small custom reader/writer would still need to be built either way.
User (answer)

Right, A is the correct choice. I want a single SVG to carry all of its own important behavior, including these animation transitions — all of it should be findable inside that one SVG. Why? Because if I swap two slides today, and there's a separate JSON file out there, would I also need to update whatever's in it? So making the SVG a self-contained system is a good decision — it'll make it much easier to exchange things going forward.

AI

That's exactly the reasoning, and stronger than what was originally given: a slide is self-contained, so swapping two pages requires touching no third file. This is the fourth time the same principle — explicit ordering, never renumbering — has come up (the slides array, per-page step scope, the effect list, and now self-containment). It's worth recording as its own ADR (ADR-0008).

A handle for audio (question 9)

AI (asking)

Video has a poster <image> as a placeholder, so it's visible. Audio has no natural visual form, yet the core invariant of the effect-list model is that every entry points at an element.

  • A (recommended) — audio must also be attached to a visible element (e.g. a speaker icon).
  • B — audio is an invisible node.
  • C — audio isn't an element at all, but a special case in the effect list that carries a src directly.

Recommending A: it preserves the invariant (C would introduce a second kind of list entry); something invisible has no handle, and future visual editing needs to be able to click it, delete it, and see which step it's on — PowerPoint's speaker icon isn't decoration, it's a selection handle, and the agent needs to be able to refer to it by name. The cost: a speaker icon will be visible on screen, including during playback — to be addressed later with a "hide during presentation" flag.

Scope for this round (question 10)

AI (asking)

The hypothesis this bullet needs to validate: a handwritten effect list, combined with a runtime that knows nothing about the deck's content, can play back PowerPoint-grade step progression — and writing that list by hand isn't painful. No command in this round writes to the effect list, so the test deck has to be handwritten by hand, which is the most honest possible test of ADR-0004's "hand-readable" promise.

In scope: multi-page support, overview thumbnails (lazily loaded), view/play modes, a fullscreen toggle, reading and executing the effect list, entrance effects (fade and appear only for now), media playback effects, images, video, audio.

Out of scope: any write commands, agent involvement, emphasis/exit/motion-path families, with-previous/after-previous, transitions between slides, pausing and rewinding media, progress indicators.

Two things recommended alongside this: HTTP Range support (without it, Safari may simply refuse to play MP4), and having the server reject requests with Origin: null (a blind spot that only became real the moment question 6 turned on allow-scripts). One risk flagged: this round has no agent involvement at all, a first for the project; that's a deliberate choice by the user, and write commands should be added in the next round.
