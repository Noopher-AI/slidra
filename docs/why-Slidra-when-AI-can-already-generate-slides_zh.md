# Why Slidra When AI Can Already Generate Slides 

**從開放式生成走向受治理的Harness，也從單向適應走向共同的工作方式。**

## TL;DR

- AI 已經能夠生成令人驚豔的簡報。Slidra 關注的是接下來的階段：將這項能力置於受治理的 Harness 之中，同時提供對人類友善的 UX（使用者體驗）與對 Agent 友善的 AX（Agent 體驗）。
- Slidra 透過四個邊界，將開放式生成納入受治理的框架：
  - 以 SVG 為基礎的 `.slidra` 格式，定義 Agent 能夠檢查與理解的內容。
  - CLI 定義投影片可以如何被修改。
  - Skills 與操作指引定義 Agent 應如何工作。
  - 可執行的驗證機制提供回饋，以支援持續精修。
- Slidra 同時提供 UX-friendly 與 AX-friendly 的體驗，並以 `.slidra` 文件作為唯一事實來源：
  - 人類透過直接、視覺化且 UX-friendly 的介面工作。
  - Agent 透過結構化、可程式化且 AX-friendly 的 CLI 介面工作。
  - 儘管雙方使用不同的介面，人類與 Agent 的操作都會透過同一套 CLI 修改簡報，並作用於同一份 `.slidra` 文件。
- 目標不是改善 AI 生成與人工編輯之間的交接，而是建立一套共同的工作方式，讓這種交接逐漸消失。

---

開源 AI 簡報專案已經證明，Agent 能夠研究主題、組織敘事、生成視覺內容，並組裝出完整的簡報。這些都是重要的成果，也讓簡報生成從概念展示轉變為實際可用的能力。

**我們打造 Slidra，不是因為 Agent 無法生成簡報，而是因為單靠生成，無法形成一套可靠的工作方式。**

一份生成完成的簡報很少就是工作的終點。有人會修改標題、移動圖表、替換圖片、調整動畫時間，或要求 Agent 只修改其中一個段落而不要影響其他內容。真正的挑戰，往往在初稿出現之後才開始。

這帶出了兩個問題：Agent 需要什麼樣的結構，才能在生成之後持續可靠地工作？而一個產品又該如何設計，才能讓人類留在這個過程中，同時不必放棄自己最自然的簡報編輯方式？

---

## 第一部分——從生成走向受治理的 Harness

### 初稿只是開始

AI 簡報生成最簡化的敘事通常是：

```text
提示詞 → 簡報
```

但一份簡報真正的生命週期更接近：

```text
提示詞 → 初稿 → 審閱 → 局部修改 → 驗證 → 更多修改 → 正式發表
```

生成只是這個流程中的一步，而不是流程本身。一個真正實用的系統必須在多次修改之間保留狀態、支援作用範圍明確的變更，並能判斷修改是否意外破壞了其他內容。

### 當模型掌握整個流程

在以生成為中心的系統中，每一次修改都可能變成另一項生成任務。模型必須重新理解目前狀態、推斷要求指的是哪些物件、自行決定要重寫多少內容，最後再由自己判斷結果是否仍然有效。

這使得過多責任落在模型的臨時理解之中。修改範圍可能模糊不清，無關內容可能產生偏移，而錯誤也可能被忽略，因為產生結果與評估結果的是同一個系統。

問題不在於模型不夠聰明，而在於責任配置不合理：**模型同時被要求提供創造力與控制力。**

### 治理方式的轉變

在 Slidra 中，控制力並不是來自反覆要求模型「更小心一點」，而是來自把模型置於一個結構化系統之中。

模型仍然負責研究、推理、寫作與視覺決策，但它會在明確的邊界內工作。這些邊界分別定義了什麼內容存在、哪些狀態可以改變、工作應如何進行，以及結果必須符合哪些條件。

## 治理框架的四個邊界

### 一、表示層：什麼存在於簡報中？

`.slidra` 並不是單一 SVG 檔案，而是一個 ZIP 容器。它包含 `project.json`、每張投影片各自的權威 SVG 文件，以及封裝在內的素材與字型；也可以包含範本、規劃資料、講者備註、評論、動畫效果與轉場。

SVG 仍然是視覺內容的基礎，但 Slidra 在其上加入了簡報語意，包括投影片順序、畫布尺寸、穩定且不透明的 `el-*` 物件識別碼、名稱、鎖定狀態、階層、群組、前後順序，以及時間關係。

這讓 Agent 擁有可以具體檢查的對象。它可以列出容器內容、讀取 `project.json`、查看某張投影片的 SVG、辨識既有物件，並取得有順序的動畫效果。部分幾何資訊仍需從 SVG 屬性與 transform 中解讀，但狀態存在於文件裡，而不是只存在於模型的記憶中。

### 二、操作層：什麼可以被改變？

Slidra CLI 定義了 Agent 如何改變簡報狀態。它的命令是作用範圍有限的語意操作，例如設定單一物件的文字、移動指定元素、對齊一組物件、調整前後順序、加入動畫效果，或修改轉場。

例如，修改標題不需要重新生成整張投影片；把圖片向右移動二十個像素，也不需要重寫周圍物件。命令本身會同時表達預期操作與操作目標。

```sh
slidra text set <id> slides/001.svg el-title "A New Title"
slidra element move <id> slides/001.svg el-image --dx 20 --dy 0
```

同一套命令介面同時支援建立與精修。Agent 不只能建立投影片和物件，也能執行真實簡報工作後期最常出現的細微調整。

### 三、行為層：工作應如何進行？

命令定義了什麼事情可以做，但它們本身並不會定義良好的工作紀律。因此，Slidra 還提供操作指引與 Skills，告訴 Agent 應如何負責任地使用這些命令。

這套流程刻意採取保守原則：修改前先檢查目前的投影片；使用既有物件 ID，而不是自行猜測；只進行必要的最小修改；逐步工作；盡可能保留既有風格；並在宣告完成之前驗證結果。

這些指引把彼此獨立的命令轉化為可重複執行的方法，也降低 Agent 把精確編輯任務變成不必要重寫的機率。

### 四、驗證層：哪些條件必須持續成立？

Slidra 的驗證器會提供機器可讀的檢查結果，其中包含投影片、元素、規則、實際值、限制條件與說明訊息。目前的規則涵蓋畫布溢出、文字重疊與密度、字型與填色、結構要求、講者備註、動態效果，以及與規劃資料相關的限制。

```json
{
  "slide": "slides/001.svg",
  "element": "el-title",
  "rule": "geometry.text-overlap",
  "actual": "overlap detected",
  "limit": "no overlap",
  "message": "title overlaps another text element"
}
```

驗證器目前並不是通用的視覺品質裁判，也不會自動修復每一項問題。它提供的是一個獨立的回饋介面，讓 Agent 或人類能據此決定下一步操作。Slidra 讓驗證迴圈成為可能，但不會假裝這個迴圈能自行完成。

**表示層讓投影片可被檢查；命令讓它可被操作；指引讓流程具有紀律；驗證則讓結果可以被問責。**

### 一個讓 Agent 能持續工作的世界

這四個邊界共同建立了一個世界。在這個世界裡，Agent 不只能生成內容，還能檢查既有狀態、執行範圍明確的操作、取得具體回饋，並從結果繼續工作。

這套治理框架並不會取代模型的創造力，而是為創造力提供一個穩定環境，讓每次修改得以累積，而不是造成破壞。

## 第二部分——從單向適應走向共同媒介

### Agent 的可靠性不等於人類的使用體驗

一個系統可能非常適合 Agent，卻仍然不是一個適合人類的產品。結構化格式、功能完整的 CLI 與機器可讀的驗證，確實能讓自動化更可靠，但這並不表示聊天框就是編輯視覺構圖的理想介面。

人類以空間方式編輯簡報。他們會指向、選取、拖曳、縮放、分組、比較與調整。如果要求使用者把每一個視覺意圖都轉譯成文字，就會失去直接操作所帶來的許多優勢。

### 兩種單向適應

當 Agent 被迫操作為人類設計的 GUI 時，它們必須處理座標、視覺定位、短暫的介面狀態，以及原本為手與眼睛設計的控制元件。

當人類被迫進入完全以聊天為中心的工作流程時，他們必須用語言描述原本只要指一下就能表達的關係，例如「右邊那張圖片」、「第二個方框」，或「把這個稍微移近那個標題」。

這兩種方式都只提供一個原生介面，以及一個經過轉譯的體驗。其中一方可以自然工作，另一方則必須適應。

### 共同媒介的轉變

Slidra 並不要求人類與 Agent 共用同一種介面，而是讓雙方透過各自原生的介面，操作同一個共同媒介。

對人類而言，這個介面是視覺化編輯器；對 Agent 而言，則是結構化命令介面。兩者底下都是同一份 `.slidra` 簡報，擁有相同的物件身分、文件能力與驗證規則。

GUI 會把它所支援的編輯操作導向 Agent 使用的同一個命令層。這並不表示每一個 CLI 命令都有對應的 GUI 控制項，而是表示人類與 Agent 所支援的操作最終會匯聚到相同的底層狀態，而不是產生彼此平行的簡報版本。

### UX-Friendly 意味著保留直接操作

人類應該能夠選取物件、拖曳、縮放、排列圖層、對齊群組、直接編輯文字，並調整動畫時間，同時立即看到視覺結果。

這些並不是應該被 AI 淘汰的舊式互動，而是高頻寬的視覺溝通方式。在許多情況下，兩秒鐘的拖曳動作，比一整段文字指令更能精確表達意圖。

### AX-Friendly 意味著提供結構化操作

Agent 需要的是另一種精確性。它們應能取得穩定的物件 ID、檢查文件狀態、鎖定特定元素、組合操作、接收結構化錯誤，並根據錯誤繼續工作。

AX-friendly 的介面不會模仿滑鼠操作，而是直接揭露操作背後的語意：移動這個物件、把這些元素分組、設定這個效果，或驗證這份簡報。

因此，人類與 Agent 都是一級使用者，但並不是同一類型的使用者。

### 情境資訊應在介面之間流動

最有效的協作，發生在情境資訊能於不同介面間流動，而不必全部被壓縮成文字的時候。視覺選取可以提供物件參照，使用者語言提供意圖，`.slidra` 文件提供周圍狀態，CLI 負責執行，而驗證器則提供回饋。

目前，Slidra 已透過固定在特定物件或頁面上的評論，支援這種情境流動的初步形式。這些評論可以把投影片路徑與目標 ID 帶入 Agent 的下一次提示中。更完整的自動選取情境傳遞，仍是後續發展方向。

其原則很簡單：**介面不應強迫人們用文字描述那些只要指一下就能表達的事物。**

### 一份簡報，一個連續流程

當人類與 Agent 能透過各自的介面操作同一份文件時，生成與編輯就不再需要是兩個彼此分離的模式。

Agent 可以建立初稿；人類可以移動物件並在其上留下評論；Agent 可以透過精確命令修改該物件；人類再以視覺方式審閱結果。驗證器可以指出具體問題，而任一方都能進行下一次修正。

這個流程可以依需要反覆交替，而不必匯出、重新生成，或合併彼此分離的版本。即使控制權在人類與 Agent 之間移動，文件本身仍然保持連續。

## 一套可靠的工作方式

Slidra 並不是在反對簡報生成，而是試圖讓生成成為一個更完整、更可靠流程中的一部分。

它的治理框架為 Agent 提供明確的表示方式、範圍有限的操作、工作紀律與可執行的回饋；它的共同媒介則讓人類保留直接的視覺控制，同時讓 Agent 透過結構化操作參與其中。

Slidra 為 Agent 建立了一個結構充分、能夠可靠工作的世界，也為人類提供了一個足夠靈活、能夠自然協作的媒介。

**AI 簡報的未來，不是讓生成與編輯之間的交接變得更順暢，而是建立一種共同工作方式，讓這個交接本身逐漸消失。**

## Slidra 所帶來的產品體驗

從使用者的角度來看，Slidra 不像是在 AI 生成器與傳統編輯器之間切換，而更像是與 Agent 一起在簡報中工作。

### 一、從 AI 開始，但不止於生成

使用者可以先請 Agent 建立初稿，再繼續精修同一份簡報，而不必為了開始正式編輯，就先把結果匯出到另一套工具。

### 二、保留熟悉的直接操作

使用者仍然可以在畫布上選取、拖曳、縮放、旋轉、分組、對齊、調整順序與編輯物件。使用 AI 並不代表必須放棄直接操作的即時感。

### 三、先指出對象，減少文字描述

使用者可以在選取的物件或頁面上留下評論，並把該參照帶入 Agent 的下一項任務。與其描述「圖表下方的方框」，使用者可以直接指出物件，只需說明想做什麼修改。

### 四、在人類與 Agent 之間維持同一份狀態

GUI 所支援的編輯操作與 Agent 命令會透過相同的命令層，更新同一份 `.slidra` 文件。畫布會反映 Agent 的修改，而 Agent 的後續工作也會接續使用者建立的最新狀態。

### 五、獲得具體回饋，而不只是一句「完成了」

驗證結果可以指出受影響的投影片、物件、規則、實際值與限制條件，讓問題更容易被定位，也讓 Agent 或使用者能根據具體資訊進行下一次修正。

### 六、在人工作業與 Agent 作業之間流暢交替

使用者可以先讓 Agent 建立投影片，接著手動調整構圖，再把修改要求固定到某個物件上，讓 Agent 更新後回到畫布審閱。這個流程可以反覆交替，而不會產生彼此分離的人類版本與 AI 版本。

**最終的產品體驗不再是「生成、匯出、修補」，而是「建立、檢查、調整、驗證、繼續」——人類與 Agent 共同參與同一份持續演進的簡報。**
