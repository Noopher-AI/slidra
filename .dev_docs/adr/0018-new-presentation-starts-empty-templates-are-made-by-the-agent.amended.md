# A new presentation starts empty; a plan is materialized as files inside the presentation, three roles hand off through a blocking gate, and validation is a CLI command

> **Amended (NOOP-472, re-confirming against [E6.T7]/[E6.T8]).** Decision 9 below (per-deck file lock, "every `slidra` command takes a file lock on that presentation... holding it until the process exits") still holds under the SQLite container introduced by `spec/rfcs/0001-sqlite-container-format.md`: the same per-deck advisory lock, now keyed by the deck's canonical file path rather than a work-directory path, is acquired once in `main.rs` and held for the whole command (`workspace::lock`, `crates/slidra/src/workspace/lock.rs`) — SQLite's own locking is a second, independent layer underneath it, not the mechanism doing the serializing.
>
> Two later additions read consistently with this ADR's existing shape, not against it. `plan/outline.md`/`plan/design-spec.md` remain this presentation's actual source of truth over the chat history persisted by [E6.T7]: a new agent joining a conversation is told explicitly to treat chat history as background only, subordinate to the plan files (`packages/server/src/agent/brief.ts`). And master view mode ([E6.T8]) ships as a fourth independent skill, `slidra-apply-master`, rather than folding into `slidra-build` or adding the umbrella skill decision 3 above already rejected.

`slidra new` used to ship with one undesigned placeholder page (a white background, the presentation name centered at 48px), and the `slidra-outline` skill grew an outline directly into slides: font sizes, colors, and coordinates were all instructed to "copy the reference page read in step one" — except a new presentation had nothing worth copying. That's exactly how one recurring failure mode kept showing up: slides grown from an outline never looked designed, and after a first round of "improve it," they'd turn into every page being a full paragraph of script — because no step ever forced the agent to decide "what does each page say, how much, what does it look like" before touching the canvas, and no step could objectively say "this isn't good enough."

Looking at a reference presentation-generation skill this project draws on, its quality comes from three layers: **rules** (font-size ratios, color roles, density, pacing), **process gates** (outline → author confirms → design spec locked → first-page gate → page-by-page production → validated to zero errors before delivery), and **roles with intermediate documents** (a strategist, an executor, and a reviewer, each reading its own rules, handing off via `outline.md` and `design_spec.md`). This ADR brings all three layers into this app, but built from its own materials: intermediate documents live inside the presentation itself, the gate is a window in the editor, and validation is a single command.

Five decisions:

1. **A new presentation ships with no slides at all.** `slidra new` only writes `project.json` (`slides: []`), the embedded font, and its license text. An empty presentation doesn't draw a blank white slide in the editor — it just shows one line of white text on the stage, "No slides now," and `serve` no longer refuses to run on a zero-slide deck. The first page is produced by the author or the agent.
2. **A plan is materialized as a `plan/` directory inside the `.slidra`, with exactly two files.** `plan/outline.md` (status, narrative pattern, per-page type/pacing/thesis, and questions to ask the author) and `plan/design-spec.md` (density, a six-role color scheme, font-size table). Each file opens with a fenced JSON block as its machine-readable section, followed by Markdown meant for people and agents to read. These files can only be written via `plan set|list|delete`, and read via `cat`; `plan set` validates fields before writing, and rejects the write on failure. Plans are excluded from undo history.
3. **Three roles, three skills, each independent.** `slidra-plan` (read the outline, choose a narrative pattern, plan each page, raise questions, pick a color scheme and font sizes, then write both plan files and stop); `slidra-build` (only proceeds once the plan is `confirmed`: gates on the first page, builds page by page, registers a template the first time each page type appears, and runs `validate` until it hits zero errors); and `slidra-validate` (only validates, only comments). There's no umbrella skill chaining them together; "From outline…" goes straight to `/slidra-plan`. The old `slidra-outline` skill is removed.
4. **The gate is a blocking window in the editor.** Whenever the plan file is `draft` and carries open questions, the editor pops a window that blocks every other action: a read-only page-by-page plan table, each question defaulting to the agent's suggested answer, with a togglable set of options plus free text. Three exits: "Confirm and build" bundles the answers into a `/slidra-build [Plan confirmed]` message sent back to the agent; "Re-plan" requires a note and sends a `/slidra-plan [Redo]` message; "Abandon" skips the agent entirely and just runs `plan delete`.
5. **Validation is a Rust command, `slidra validate <id> [slide-path]`.** The rules and the three density thresholds are hard-coded in Rust; color scheme, font-size table, density, and per-page type come from the plan file's JSON section; with no plan file present, only geometry and structural well-formedness are checked. Output is a list of `{ slide, element, rule, actual, limit, message }` entries, exiting non-zero on any error. The skills only interpret and fix issues — they no longer count characters or compute coordinates themselves.

6. **One SVG per slide.** `slide add --svg`/`slide set --svg` accept a whole-page SVG, running normalization and a compliance check on write (rejecting `<script>`/`<foreignObject>`, allowing `<defs>`, gradients, filters, and paths), and converting a bare `<text>` carrying `data-slidra-text-width` into a real text box (with wrapping, lists, in-place editability, and visibility to `validate`). The build skill's main action becomes "write a page following the SVG authoring guide, write it, validate it," with element-by-element commands demoted to fine-tuning tools. This mirrors the executor model of the reference skill, and is the precondition for genuinely polished output: what a command set can compose is limited; what can be written directly in SVG isn't.
7. **One visual language, with animation on by default.** The reference design guide is rewritten as an "editorial/tech" visual language: an SVG authoring guide with a fixed stage (a full-bleed circle, footer, and dynamic page number), a full example SVG for each of six page types, and an entrance script for each. The build step applies the plan's `animation` setting (full/minimal/none, an extra question in the plan window) via `effect add` and a whole-deck fade transition. Animation is this app's point of differentiation against export-oriented tools, so it defaults to on.
8. **A background image is an asset plus a locked, full-bleed image element.** `asset import --svg` lets the agent build an SVG asset from command-line content (it still can't write files directly); `slide background set --asset` places it as a locked, full-bleed `<image>` tagged `data-slidra-role="background"` at the bottom of that page's stack. This reuses the existing asset, image, lock, and z-order machinery — in the editor it's just one object, and the same image can be shared across pages. The guide provides four background recipes; `validate`'s `structure.scrim` check guarantees that any page with a background image still keeps its text sitting on a semi-transparent panel. Rejected: a page-level `--background-image` property (three separate rendering paths would each need their own handling), and painting the background as dozens of raw primitives at the bottom of the whole-page SVG (impossible to select correctly, can't be shared, can't be swapped with one command).
9. **Commands against the same presentation are mutually exclusive through the CLI.** An agent may fire off commands in parallel; two processes reading, modifying, and writing the same SVG at once would corrupt `<slidra:effects>`. Every `slidra` command takes a file lock on that presentation once it resolves which one it's operating on, holding it until the process exits — parallel calls are therefore safe, but serialized rather than concurrent.

## Why templates are built fresh instead of shipped

Shipping a template ready-made runs into the problem that it gets designed before anyone knows what the author actually needs: theme, tone, and color scheme are all fixed in advance, and the agent can, at best, tweak colors and font size afterward. Instead, a template gets built fresh by the build step according to the plan, then registered with `template add` — its style follows the author's outline and the choices they made at the gate, and it uses nothing but existing commands, without touching the container format at all. Registering it as a template preserves the product concept from ADR-0013: it's visible in the New panel's Layouts, and creating a new slide afterward reuses the same set. "`new` ships with a neutral starter template" is deferred to a follow-up, as the starting point for anyone who skips the agent entirely.

## Why the gate is a window, not a conversational convention

Pasting a table into the conversation and asking the author to reply "OK" leaves nothing in the way if the author instead just types the build command directly — the gate would exist in name only; having the build step ask again itself would mean answering twice. A window turns "this step needs the author's judgment call" into actual product behavior: the agent's suggestions are the defaults, the author reviews and presses one button, and the answer comes back to the conversation in a fixed format, which the build step uses to flip the plan to `confirmed`. Being blocking is deliberate: editing slides before the plan is settled doesn't make sense; "abandon" is the only exit that doesn't go through the agent, guaranteeing the author can always get out.

## Why validation is a command, not a table inside a skill

The reference checker is a script, not something relying on a model's impression of the numbers; the first version of the validation skill had the agent count characters itself and compute `y + line-count × 1.45 × font-size` by hand — exactly the approach the reference tool avoids. With the thresholds moved into Rust, the agent gets back something like "page 2, item 3 has 23 characters, limit is 18" — an actionable error, not a table it has to check itself.

## Considered Options

- **`new` ships with a neutral starter template**: gives someone who skips the agent entirely something to work with, and is the most stable and testable option; but its style is fixed and unrelated to what the author actually needs. Deferred as a follow-up, not a replacement for building fresh.
- **A working-directory library of "many styles × many page types" SVGs, pasted in by a skill via `element paste --svg-file`**: theoretically the most flexible, but it pastes elements rather than a whole page, isn't visible to a person browsing templates in the editor, and effectively bypasses the "template" concept entirely.
- **Keep the placeholder page, and have a skill detect "still untouched" and overwrite it as a cover**: the detection condition is fragile — the author changing one character breaks it — and an empty presentation is already well-supported by both the frontend and the CLI.
- **Only add the rules layer, skip the gate and the roles**: doesn't address the root cause of the original failure (no planning before building, no objective validation afterward).
- **Keep the plan only in the conversation**: it's gone the moment you switch agents, switch machines, or come back the next day; `validate` also has no rules to read for "what this particular presentation requires."
- **Store the plan in a `project.json` field**: long Markdown crammed into JSON is unreadable, and `cat project.json` would mix canvas settings together with the whole plan.
- **A single umbrella skill chaining plan → build**: the routing approach the reference skill uses; but the window already owns the gate, and chaining would make "redo just a few pages" or "validate on its own" awkward to invoke separately.
- **A dismissible window, reopened via a status-bar badge**: gentler, but the author would edit slides while the plan is still unsettled, defeating the point of the gate.
- **Frontmatter in YAML**: closest to the reference skill's convention, but the Rust crate has no YAML dependency, and YAML's single-quote conventions clash with the CLI's own quoting rules.
- **`validate` rules entirely hard-coded, never reading the plan file**: an author's custom color scheme would get flagged as wrong, and the plan file would have no bearing on validation at all.
- **Let the agent write files directly**: the most direct way to do one-SVG-per-slide, but it overturns ADR-0004; the `--svg` flag keeps "every change goes through a command" intact, while still allowing normalization and rejection on write.
- **Have the agent lay out each line of a bare `<text>` itself**: the smallest Rust change, but text wouldn't wrap, there'd be no lists, it wouldn't behave as a text box in the editor, and `validate` couldn't see character counts.

## Consequences

- Every test or script that used to go straight from `new` to editing `slides/001.svg` now needs a `slide add` first; the CLI spec's section on `new` documents the zero-slide start.
- The command count grows (`plan set|list|delete`, `validate` added); the container format spec gains a `plan/` section; the command reference is updated to match.
- The experience after "From outline…" is: paste an outline → the agent writes a plan → a window appears → press confirm → the agent builds to zero errors. Quality still depends on the agent following the plan, but every step now leaves something to inspect: the plan file, the window's answers, `validate`'s error list.
- The frontend gains a state that blocks the whole editor; any change event touching `plan/` needs to open and close the window correctly.
- The command count grows again (`slide set` added); `slide add` gains `--svg`. A text-box declaration is an **input shape**, not the storage shape — what's actually saved into the `.slidra` is always the structured form produced by `textbox add`.
- There is currently only one visual language (`design-spec.visual: editorial-tech`); a second one means writing another guide and giving the planning step a question to choose between them.
