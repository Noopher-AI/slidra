# The agent runs in an OS sandbox, and so does the CLI

> The follow-up ADR-0019 named by name: its Cost section's closing paragraph said getting both "commands are unrestricted" and "the blast radius stays bounded" at once "requires taking execution back under control... and putting subprocesses inside an OS-level sandbox. That's a follow-up to this decision, not a substitute for it." This is that follow-up.

ADR-0019 traded a narrow, discipline-enforced allowlist for "any shell command is allowed, only `slidra`'s own gate stops a command from touching presentation content" — and named its own cost plainly: the blast radius grows from one presentation to the whole machine, and the prompt-injection chain (web search results, imported URLs, pasted articles, all reaching the agent's context) is open, because nothing downstream of the allowlist depended on trusting the agent's *intent*, only on blocking specific paths by name. That gap needed an OS-level backstop, not another string check.

## Decision: two sandboxes, facing opposite directions

1. **The agent sandbox.** Every process the connected agent spawns runs wrapped in an OS write-isolation layer: the kernel's own Landlock LSM on Linux (`landlock-launcher.ts`, via the `slidra-sandbox-exec` helper binary), Seatbelt via `@anthropic-ai/sandbox-runtime` on macOS (`srt-launcher.ts`), and no OS-level path on Windows (`passthrough-launcher.ts`, unconfined by design — see "Windows" below). A write outside the agent's own sandbox root and a small, reviewed allow-list is refused **by the OS itself**, not by a string check over the command the agent asked to run — the exact class of check ADR-0019 already conceded a determined adversary (or a sufficiently creative shell one-liner) could route around.
2. **The CLI sandbox, in reverse.** The shim wrapper on the agent's `PATH` (`<sandbox root>/bin/slidra`, `sandbox/shim-wrapper.ts`) runs `slidra <args>` on the agent's behalf against a *second* policy (`buildCliSandboxPolicy`), scoped to the deck's own parent directory plus `SLIDRA_HOME` and `tmpdir()` — the CLI's own write path is sandboxed too, separately from the agent process that invoked it.

This is not symmetrical, and it is not meant to be: the agent sandbox stops the agent's shell from writing outside its scratch area; the CLI sandbox stops `slidra extract <deck> ~/.ssh/` (a legitimate command, an illegitimate target) from reaching anywhere the CLI itself isn't supposed to write.

## Why not an allow-list of commands or flags

ADR-0019 already discarded this shape once — the original ACP permission hook's `slidra *`-only allowlist — and the reasons hold, more strongly, for a second attempt: a command/flag allowlist has to enumerate every legitimate shape in advance (`sed`, `find`, a program reading a path from stdin, a shell variable assembled at runtime — the exact case `os-enforcement.test.ts`'s AC1 test constructs to prove a string check cannot catch it) and drifts the moment a new tool or invocation shape shows up. It is a signpost an agent can be argued past, not a fence. This ADR does not revive that shape in any form; write isolation here is enforced by the kernel against the process's actual syscalls, never by inspecting the command string first.

## Why the shim makes the CLI sandbox not optional

`slidra` on the agent's `PATH` is not the real binary — it is a shim (`shim-wrapper.ts`) that forwards to `slidra` running under its own policy via the shim endpoint (`shim-endpoint.ts`). If the CLI itself ran unsandboxed on the agent's behalf, the agent sandbox's write restriction would be moot: `slidra extract <deck> <anywhere-writable>` is a single `slidra` invocation, and the agent sandbox's allow-list already has to grant the CLI's own working paths for ordinary editing to work at all. The CLI sandbox is therefore not a defense-in-depth nicety — it is the thing that makes the agent sandbox's guarantee actually hold for every avenue a `slidra` command opens, not just direct shell writes.

## The write allow-list is a standing trade-off, not a solved problem

`buildAgentSandboxPolicy`'s allow-list (`packages/server/src/sandbox/policy.ts`) grants, beyond the sandbox root itself: the whole OS temp directory (so npm/pip/uv/playwright caches and `/dev/null` redirection keep working — a shell idiom as common as `cmd > /dev/null 2>&1` would otherwise fail with EACCES the moment Landlock treats opening `/dev/null` for writing as a write); `~/.claude`, `~/.claude.json`, `~/.codex` (session state and credential refresh); `~/.npm` and the platform cache directory; and `~/.config` — the widest entry, reviewed and accepted rather than overlooked, because many CLIs (`gh` among them) keep long-lived tokens there and it is the one directory here not scoped to a single tool. Every entry exists because some real, currently-shipping agent tool breaks without it (AC4: existing credentials and CLI logins keep working with no extra configuration) — this is not a gap waiting to be closed, it is the actual, ongoing shape of the trade-off: a wider allow-list is a wider write surface, by construction, for as long as the agent's own tooling needs these paths.

## Platform support

Linux (Landlock) and macOS (Seatbelt) are both supported and tested against a real spawned process, not a mock (`os-enforcement.test.ts`'s Landlock and Seatbelt describe blocks respectively). Windows has no OS-level write-isolation path at all — `createSandboxLauncher()` returns a passthrough launcher with `active: false` and a degraded reason, and the agent runs unconfined there. This is a deliberate scope line, not a gap nobody noticed: `SLIDRA_SANDBOX=off` already exists as an explicit escape hatch for forcing the same unconfined behavior on a platform that does support isolation, and startup itself never fails because write isolation could not be established — a dependency/init/self-check failure on Linux or macOS degrades to the same passthrough launcher, with a reason attached, rather than refusing to start `slidra serve` at all.

## What this does not fix

Neither sandbox restricts what a spawned process can **read** or reach over the **network** — `landlock-launcher.ts`'s ruleset is built from `AccessFs::from_write` alone, and has no read-restriction concept to apply `SandboxPolicy.denyRead` to even though `policy.ts` still computes it (macOS's Seatbelt path does consume it — see the ADR-0002/ADR-0004 amendments). This is deliberate, not an oversight: AC3 requires the network path and unrelated-file reads to stay open, since the agent's own tools (search, fetch, `cat` on project files) depend on it. It follows that **ADR-0019's prompt-injection chain stays exactly as open as ADR-0019 already said it was** — a sandbox that only ever restricts writes cannot be, and was never meant to be, a defense against an agent reading a malicious instruction and repeating it back as a command of its own choosing. See ADR-0019's amendment for the explicit statement of this boundary.

## Considered Options

- **bubblewrap/user namespaces on Linux** (what `@anthropic-ai/sandbox-runtime`'s own `initialize()` requires there): rejected — it unconditionally requires `bwrap`/`socat`, which in turn needs an unprivileged user namespace, disabled by default on most Linux distributions' machines. Landlock needs no such namespace and no root.
- **One shared launcher abstraction reused verbatim on every platform**: rejected — Linux and macOS have genuinely different primitives (Landlock's write-only ruleset vs. Seatbelt's fuller filesystem/network profile), and forcing one config shape across both would mean either under-using Seatbelt's read-restriction capability or inventing a Landlock feature that does not exist. `SandboxLauncher` is the shared seam; `SandboxPolicy` is a plain, launcher-agnostic shape; each launcher interprets it according to what its own OS primitive can actually do.

## Consequences

- A dependency/init/self-check failure on any platform degrades to the unconfined passthrough launcher with a reason attached, rather than failing `slidra serve` startup — write isolation is a best-effort hardening layer, never a precondition for the app to run at all.
- The agent sandbox's allow-list has to be revisited every time a newly supported agent tool needs a new credential/cache path — this is expected maintenance, not a design flaw (see "standing trade-off" above).
- Every claim this ADR makes about enforcement is backed by a test that spawns a real process through the real launcher, never a mock of the OS primitive (`os-enforcement.test.ts`, both the Linux and the macOS describe blocks) — "tested on the `SandboxLauncher` interface, never on `slidra-sandbox-exec`'s argv shape."
