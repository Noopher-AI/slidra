N-01

Drag-to-move elements is completely broken — holding and dragging produces no response

P1 Blocker New this round · Regression Direct manipulation
Reproduction
  1. On Slide 1, click the title “Acceptance Demo Deck” to select it.
  2. On the title, hold the left mouse button, drag to a new position, and release.
Actual
During the drag there is no preview and no snap guide lines; after release the element stays where it started. slides/001.svg has no transform written and no Undo-able history step is produced. The console shows no errors. Retrying on a freshly inserted text element that already carries transform="translate(107.52 302.4)" gives the same result.
Control
Same element, same CDP event sequence: dragging the top-right handle to resize works correctly (Step 1’s font-size 40 → 42.54; the Slide 1 title 86 → 99.0). So the gesture pipeline is alive — the only thing broken is move.
Regression evidence
Same demo, same operations: on the previous round’s 899bed3 this moved the title to the new position and updated the left-rail thumbnail instantly (see the previous report’s “Confirmed working: drag to move elements”). This round on db6d497 it does not move no matter what. The only relevant change between the two rounds is 81c4e74 “browser goes engine-free — DOM/CLI replace @Slidra/core”.
Expected
05-INTERACTIONS.feature “Move and resize elements › drag snap”: dragging a selected element moves it; when it nears an edge it snaps and shows pink guide lines; on release it becomes one Undo-able history entry.
Impact
Drag-to-move is the most basic action of a visual editor, and the GUI has no alternative — the right rail’s Style › Object has no position field, and Arrange can only align/distribute, not freely position. To move any element the author is left with the terminal command Slidra element move. With that path broken, the editor cannot edit layout.
Suspected scope
beginMoveGesture in canvas.ts (:2413) silently bails out when any of selectionIds / currentSlideModel / viewport is absent, and also when originals.size === 0. currentSlideModel being null is ruled out (Ctrl+A still selects all three elements, and that path depends on it too), as is viewport being null (the resize gesture depends on it and works).')

F-03

Right after opening, without changing a single character, the title bar already says “Unsaved changes”

P3 Moderate Fixed Save state
Re-verification this round
Fixed, and fixed for this exact cause. Running Slidra open on the same .slidra six times in a row reported clean all six; on one of them the raw floating-point reading differed by +0.000488 ms (the old logic would judge this dirty), and the new logic floors both sides to whole milliseconds and correctly judges it clean.
Fix
readSaveState in packages/server/src/slidra/save-state.ts was changed to Math.floor(maxMtimeMs) > Math.floor(entry.savedAt), with a comment explicitly stating this is to eliminate the last-digit floating-point difference between Rust’s as_secs_f64() * 1000.0 and Node’s mtimeMs — consistent with the 1-ULP phenomenon reported in the previous round.

F-01

Slides are crushed by browser scrollbars — both while editing and during actual playback

P2 Critical Still reproduces Stage · Playback
Re-verification this round
Still reproduces. div.stage has clientHeight 459 and scrollHeight 462; the right and bottom edges of the slide are each still crushed by a white scrollbar (with up/down arrows).
Actual
The extra 3px comes from the baseline gap of <svg> as an inline replaced element. The thumbnail wrapper already has svg{display:block}; the two used by the main stage and playback do not.
Expected
A slide is a fixed-aspect canvas and should never show scrollbars under any circumstance; playback mode is supposed to be “black background, full frame”.
Impact
While editing, the author will mistake it for a broken element or layout they inserted, and the scrollbars cover about 15px on the right and bottom; during playback the scrollbars appear directly on the audience-facing screen, and there is no setting to turn them off.
Clue
The three srcdoc wrapper functions at canvas.ts:4157 (view) / :4223 (select) / :4262 (playback) all only set <body style="margin:0;background:#fff">, without overflow:hidden, and the SVG has no display:block either.
